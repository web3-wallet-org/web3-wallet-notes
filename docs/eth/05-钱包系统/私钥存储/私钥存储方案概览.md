
## 核心问题
交易所/托管钱包需要服务端持有私钥，如何在保证安全的前提下做到可扩展、可运维。

---

## 四种方案对比

| 方案 | 安全等级 | 成本 | 可扩展性 | 适用场景 |
|------|----------|------|----------|----------|
| CloudHSM | ★★★★★ | 高 | 一般 | 交易所热钱包、高净值托管 |
| TEE + KMS/S3 | ★★★★ | 中 | 好 | 常规交易钱包、大规模地址体系 |
| KMS + S3 | ★★★ | 低 | 好 | 内部服务、测试环境 |
| wallet.data | ★★ | 极低 | 好 | 测试、临时、小规模项目 |

安全等级：CloudHSM > TEE+KMS/S3 > KMS+S3 > wallet.data

---

## 1. CloudHSM

**本质**：云厂商（AWS、Google）提供的托管硬件安全模块，私钥存在物理硬件内部，永远无法导出。

**签名流程**：
业务系统构造 32 字节消息 hash → 传入 HSM → HSM 返回签名 → 业务组装完整交易广播

**工程要点**：
- 调用方式与 KMS 类似，但底层是独占的物理硬件
- AWS CloudHSM 需要部署在 VPC 内，通过 CloudHSM Client 访问
- 密钥容量有上限，不适合为每个用户单独建密钥（通常用派生方案）

**选型信号**：监管合规要求、大额资产托管、交易所核心热钱包

---

## 2. TEE（可信执行环境）

**本质**：CPU 级别的硬件隔离执行环境，代码和数据在 enclave 内运行，外部无法读取。
- AWS 实现：Nitro Enclave
- Intel 实现：SGX

**签名流程**：
离线签名代码封装进 enclave → enclave 启动后通过 vsock 与外部通信 → 签名过程中私钥始终不暴露在非安全环境

**存储问题**：
部分 TEE 环境（如 Nitro Enclave）**没有持久化存储能力**，需要配合外部存储：
- 私钥加密后存 S3 或数据库
- enclave 启动时从外部拉取，解密在 enclave 内完成
- 本质是 TEE + KMS/S3 的组合方案

**工程要点**：
- Nitro Enclave 与父实例只能通过 vsock 通信，网络完全隔离
- 需要做 attestation（远程证明），验证 enclave 代码未被篡改

**选型信号**：需要兼顾安全和成本、大规模用户地址体系

---

## 3. KMS + S3

**本质**：AWS KMS 管理加密密钥，私钥加密后存 S3 或数据库。

**与 CloudHSM 的关键区别**：
- KMS 的密钥可以导出（加密形式），CloudHSM 的密钥物理上不能离开硬件
- KMS 安全边界依赖云厂商，CloudHSM 安全边界是物理硬件

**工程要点**：
- IAM 权限最小化，签名服务只授予 `kms:Sign`、`kms:GetPublicKey`
- 调用 KMS 签名需处理 DER 格式转换、v 值计算、Low-S 规范化（见 [[KMS]] 详细笔记）
- 注意 KMS 的 TPS 限制和延迟

**选型信号**：中小型钱包项目起步阶段，或内部非核心业务

---

## 4. MPC（多方安全计算）

**本质**：私钥生成时即拆分为多个碎片，分布在不同节点，签名时通过密码学协议联合计算，完整私钥**永远不在任何地方重建**。

**与 SSS（Shamir 密钥共享）的区别**：
- SSS：签名前需要重建完整私钥 → 重建瞬间存在暴露风险
- MPC/TSS：各节点直接参与计算，完整私钥从不存在 → 无单点风险

**工程要点**：
- 实现复杂，通常使用第三方库（如 tss-lib、ZenGo 的开源实现）
- 签名延迟比 KMS 高（需要多轮网络通信，100~500ms）
- 节点碎片可动态管理，支持更换持有方而不更换地址

**选型信号**：交易所冷热钱包分离、机构级大额资产、需要多人审批流程

## 工程选型决策树

```
需要最高安全 + 合规？
├─ 是 → CloudHSM
└─ 否
   ├─ 需要去除单点私钥风险？
   │  ├─ 是 → MPC
   │  └─ 否
   │     ├─ 大规模用户地址 + 成本敏感？
   │     │  ├─ 是 → TEE + KMS/S3
   │     │  └─ 否（中小规模）→ KMS + S3
   └─ 测试/临时环境 → wallet.data
```

## 面试高频

**Q: 交易所热钱包的私钥存哪里？**
分层回答：① 最高安全用 CloudHSM，私钥物理隔离不可导出；② 兼顾成本和安全用 TEE（如 AWS Nitro Enclave），签名在 enclave 内完成；③ 中小规模用 KMS，私钥托管给云厂商但有 IAM 控制；④ 测试环境才用本地加密文件。

**Q: CloudHSM 和 KMS 怎么选？**
核心判断标准：是否需要物理级别的密钥隔离。CloudHSM 是独占硬件，即使云厂商也无法拿到私钥；KMS 是多租户托管，依赖对云厂商的信任。有合规要求（如金融监管）选 CloudHSM，一般业务 KMS 够用。

**Q: MPC 和多签有什么区别？**
多签（Multisig）是链上合约层面的，需要多个完整私钥各自签名，链上验证；MPC 是密码学层面的，私钥从未完整存在，签名结果在链上看起来和普通单签一样。MPC 更灵活，无链上成本，但实现复杂。

**Q: MPC 和 SSS（Shamir 密钥共享）有什么区别？**
SSS 签名前需要把碎片聚合重建完整私钥，重建瞬间存在单点暴露风险；MPC/TSS 各节点直接参与分布式计算，完整私钥永远不重建，安全性更高。

**Q: TEE 方案中私钥存在哪里？**
TEE 本身（如 Nitro Enclave）没有持久化存储，私钥加密后存在 S3 或数据库，enclave 启动时拉取并在内部解密。加密密钥由 KMS 管理，解密操作只在 enclave 内完成，外部无法读取明文。

**Q: 签名服务为什么要和业务系统物理隔离？**
防止业务系统被攻破后横向渗透到签名服务。签名服务不能直接暴露在公网，只能接受来自内部白名单服务的请求，且只执行签名操作，不处理任何业务逻辑。
