
## 核心难点与解决方案

### nonce 并发冲突
问题：多个提币请求同时发出，各自读取链上 nonce，导致 nonce 重复，后提交的交易覆盖前一笔。

解决：
- 用单线程或分布式锁（Redis）集中分配 nonce
- 本地维护 pending nonce 计数，不每次都查链上

### 交易卡死
原因：发出时 gas 设置过低，base fee 上涨后交易长期不被打包。

解决：
- 发送 replace-by-fee（RBF）交易：相同 nonce，提高 maxFeePerGas（至少涨 10%）
- 监控 pending 时间，超过阈值自动触发加速

### reorg 导致充值回滚
问题：区块被重组后，已入账的充值交易消失，造成资金损失。

解决：
- 充值不以区块数为准，等待 finalized 状态
- 数据库记录充值状态机（pending -> confirming -> confirmed），支持回滚
- 定期核对链上状态与本地记录

### ERC20 兼容性问题
- 部分代币 transfer 不返回 bool，直接调用会 revert -> 使用 SafeERC20
- decimals 不统一（6位 USDC vs 18位 ETH）-> 入库时统一换算，展示时按 decimals 还原
- 代币合约可升级或有黑名单逻辑，转账可能静默失败 -> 检查 tx receipt 中的 logs

### 节点不稳定
问题：单节点 RPC 超时、返回数据不一致、掉块。

解决：
- 接入多个节点（自建 + 第三方如 Infura/Alchemy）
- 请求层做负载均衡和故障切换
- 关键查询（如确认数）多节点交叉验证

## 优化方向

### 批量提币
- 将多笔小额提币合并为一笔合约调用，节省 gas
- 需要部署批量转账合约，注意合约安全审计

### 多链支持
- EVM 兼容链（BSC、Polygon、Arbitrum 等）共用大部分代码
- 差异点：chainId、gas 机制（L2 有额外 L1 data fee）、finality 时间

## 监控指标
- 提币成功率（广播成功 / 最终上链）
- pending 队列长度（超阈值告警）
- 平均确认时间
- gas 消耗趋势
- 节点响应时间和错误率
