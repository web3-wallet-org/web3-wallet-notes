
## 核心问题
跨链桥转账的资金不是通过普通 ETH 转账到达用户地址的，而是由**桥合约在内部调用中**完成转账。普通充值监听逻辑完全感知不到这笔钱，导致漏记。

---

## 为什么普通监听会漏掉

普通 ETH 充值监听逻辑：
```
tx.to == 用户地址 && tx.value > 0  →  入账
```

跨链桥充值的链上结构：
```
tx.to   = 桥合约地址（不是用户地址）
tx.value = 0（主交易没有转 ETH）
Internal Transaction: 桥合约 → 用户地址，转 0.045 ETH
```

真实转账藏在 **Internal Transaction** 里，`eth_getTransactionReceipt` 拿不到，普通扫块逻辑直接跳过。

---

## 跨链桥的工作原理

以"锁定-释放"模型为例：

```
源链（如 Arbitrum）                    目标链（ETH 主网）
用户 → 调用桥合约锁定资产
                    → 链下 Relayer 监听锁定事件
                    → Relayer 在目标链提交证明
                                        → 桥合约验证后释放资产
                                        → internal call 转给用户
```

用户在目标链看到的这笔，是桥合约通过内部调用完成的，所以主交易 value=0。

---

## 正确识别跨链桥充值

### 方案：trace 接口

必须调用节点的 trace 接口，拿到完整内部调用树：

```
debug_traceTransaction(txHash)   # Geth 原生
trace_transaction(txHash)        # Parity 风格，结构更清晰
```

遍历所有 `CALL` 类型操作，找到：
```
call.to == 用户充值地址 && call.value > 0
```

### 扫块完整流程

```
监听新区块
  → eth_getBlockByNumber 拿所有 txHash
  → 过滤：tx.to 在已知桥合约白名单中
  → 对命中的 tx 调用 trace_transaction
  → 遍历内部调用，找 to == 用户地址 && value > 0
  → 记录入账，等待确认数达标
```

### 为什么要先过滤桥合约白名单

不能对每笔交易都 trace，trace 接口消耗大、慢，会打爆节点。
只对 `tx.to` 是已知桥合约地址的交易做 trace，其余走普通逻辑。

---

## 工程注意点

### 1. 唯一键设计
同一笔 tx 内部可能有多个 internal call 转给同一地址（极少但存在）。
入账唯一键必须用：`txHash + traceIndex`，不能只用 txHash。

### 2. 确认数以主交易为准
Internal transaction 没有独立的确认数，以**主交易所在区块的确认数**为准，达到阈值后入账。

### 3. reorg 处理
与普通充值一致，等 finalized 或固定确认数（12个），不要提前入账。

### 4. ERC20 通过桥转入
ERC20 跨链走的是合约 `Transfer` 事件的 logs，不是 internal tx，是另一套逻辑：
```
解析 tx receipt 的 logs
→ 找 topic[0] == Transfer 事件签名
→ topic[2]（to 地址）== 用户地址
→ 入账
```
两套逻辑（internal tx + logs）都需要支持。

### 5. 节点能力要求
| 节点类型 | 是否支持 trace |
|----------|----------------|
| 自建 Geth（full node） | 需加 `--gcmode=archive` |
| Alchemy | 支持，提供 `alchemy_getAssetTransfers` |
| Infura | 部分套餐支持 |
| 公共 RPC | 通常不支持 |

生产环境推荐用 Alchemy 的 `alchemy_getAssetTransfers`，可以直接按地址过滤所有类型转账（包括 internal），省去自己遍历 trace 的工作量。

## 面试高频

**Q: 为什么跨链桥充值会漏记？**
普通监听只看 `tx.to == 用户地址 && tx.value > 0`，跨链桥的真实转账发生在合约内部调用（internal transaction）中，主交易的 to 是桥合约、value 是 0，普通逻辑直接跳过。

**Q: 怎么解决？**
用 `trace_transaction` 或 `debug_traceTransaction` 拿到内部调用树，遍历找 to 是用户地址且 value > 0 的 CALL。为避免性能问题，只对 to 地址在桥合约白名单中的交易做 trace。

**Q: internal tx 的入账唯一键怎么设计？**
`txHash + traceIndex`，不能只用 txHash，因为同一笔交易可能有多个 internal call 到同一地址。

**Q: ERC20 跨链桥和 ETH 跨链桥识别方式一样吗？**
不一样。ETH 通过桥是 internal call（无 logs），ERC20 通过桥是合约 Transfer 事件（在 logs 里），需要两套独立逻辑分别处理。

**Q: trace 接口有什么限制？**
调用开销大，不能对每笔交易都 trace。必须先用桥合约白名单过滤，只对命中的交易调用 trace。另外普通 full node 不一定开启 trace，需要 archive 模式或第三方增强 API。
