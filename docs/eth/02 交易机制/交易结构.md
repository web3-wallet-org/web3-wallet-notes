## 1. 先给结论：钱包最常处理的是哪几类交易
- 日常钱包发送交易，主流是 **EIP-1559（Type 2）**。
- 你仍会遇到 **Legacy（Type 0）**，尤其在老链、老节点或某些 SDK 兼容路径。
- **EIP-2930（Type 1）** 在钱包前端不常主动构造，但节点/工具链会支持。
- **EIP-4844（Type 3）** 是 blob 交易，主要在特定场景使用；钱包通常需要“识别+正确展示”而不一定手动构造。

<a id="sec-2"></a>
## 2. 交易类型总览（Type 0/1/2/3）

| 类型 | EIP | 费用模型 | 关键字段 | 钱包常见度 |
| --- | --- | --- | --- | --- |
| Type 0 | Legacy | `gasPrice` 单字段 | `gasPrice` | 中 |
| Type 1 | EIP-2930 | `gasPrice` + `accessList` | `accessList` | 低 |
| Type 2 | EIP-1559 | `maxFeePerGas` + `maxPriorityFeePerGas` | 双费用上限 | 高 |
| Type 3 | EIP-4844 | Type2 + Blob Fee | `maxFeePerBlobGas` / `blobVersionedHashes` | 中低（场景化） |

<a id="sec-2-1"></a>
### 2.1 Legacy 交易（Type 0）
- 无 typed 前缀，raw tx 直接是 RLP 列表。
- 费用只靠 `gasPrice`，不区分 base fee 与 tip。
- EIP-155 后通过 `chainId` 参与签名哈希，防止跨链重放。

<a id="sec-2-2"></a>
### 2.2 EIP-2930 交易（Type 1）
- 交易字节前缀是 `0x01`。
- 在 Legacy 基础上增加 `accessList`，可提前声明访问的地址和 storage key。
- 费用仍是 `gasPrice` 模型。

<a id="sec-2-3"></a>
### 2.3 EIP-1559 交易（Type 2）
- 交易字节前缀是 `0x02`。
- 使用 `maxFeePerGas`（总上限）和 `maxPriorityFeePerGas`（小费上限）。
- 这是钱包业务最应该重点打磨的类型（推荐、加速、取消都围绕它）。

<a id="sec-2-4"></a>
### 2.4 EIP-4844 Blob 交易（Type 3）
- 交易字节前缀是 `0x03`。
- 在 Type2 基础上增加 blob 相关费用与哈希字段。
- 网络传播层包含 sidecar（blobs/commitments/proofs）；签名消息与 sidecar 是分离的。

<a id="sec-3"></a>
## 3. 交易字段逐项拆解（钱包视角）

<a id="sec-3-1"></a>
### 3.1 `nonce`
- 含义：该账户发出的交易序号，必须严格递增。
- 钱包实践：始终优先取 `pending` 视图（`eth_getTransactionCount(address, "pending")`）。
- 并发发送必须有 nonce 管理器，否则高概率撞 nonce。

<a id="sec-3-2"></a>
### 3.2 `to`
- 普通转账/合约调用：`to` 为目标地址。
- 合约创建：`to` 为空（通常 `null` 或省略），`data` 为 init code。
- 钱包 UI 必须区分：EOA 地址 / 合约地址 / 代理合约地址。

<a id="sec-3-3"></a>
### 3.3 `value`
- 单位是 wei。
- 对 ERC-20 转账，通常 `value = 0`，转账金额在 `data` 中。
- 对 payable 合约调用，`value` 与 `data` 可同时非零。

<a id="sec-3-4"></a>
### 3.4 `data`
- 语义：合约调用数据（calldata）或合约部署字节码（init code）。
- 钱包核心能力：
  - 方法识别（selector + ABI）。
  - 参数解码（人类可读展示）。
  - 风险提示（`approve`、`setApprovalForAll`、高风险方法）。

<a id="sec-3-5"></a>
### 3.5 `gasLimit`
- 含义：这笔交易最多可消耗多少 gas。
- 典型流程：`eth_estimateGas` 估算后增加 buffer（例如 10%~30%）。
- 太低会 `out of gas`，太高不会全额扣除（按实际 `gasUsed` 计费）。

<a id="sec-3-6"></a>
### 3.6 费用字段（`gasPrice` / `maxFeePerGas` / `maxPriorityFeePerGas`）
- Type0/1：只用 `gasPrice`。
- Type2/3：使用 EIP-1559 双字段。
- 加速交易本质：同 nonce 替换，提高费用参数。

<a id="sec-3-7"></a>
### 3.7 `chainId`
- 强制防跨链重放字段。
- 钱包发送前必须和当前网络 chainId 做严格一致校验。
- 多链钱包常见事故就是 chainId 不匹配签名。

<a id="sec-3-8"></a>
### 3.8 `accessList`
- 结构是 `(address, storageKeys[])` 列表。
- 能否省 gas 取决于实际访问模式，不是“加了就省”。
- 钱包通常支持透传，少量场景自动生成。

<a id="sec-3-9"></a>
### 3.9 `maxFeePerBlobGas` 与 `blobVersionedHashes`
- Type3 专属字段。
- 钱包展示要把“执行 gas 费用”和“blob 费用”分开展示，避免用户误解。

<a id="sec-4"></a>
## 4. 编码与签名：钱包到底签了什么

<a id="sec-4-1"></a>
### 4.1 Raw Transaction 基本形态
- Type0: `rlp([nonce, gasPrice, gasLimit, to, value, data, v, r, s])`
- Type1: `0x01 || rlp([... , accessList, yParity, r, s])`
- Type2: `0x02 || rlp([... , accessList, yParity, r, s])`
- Type3: `0x03 || rlp([... , accessList, maxFeePerBlobGas, blobVersionedHashes, yParity, r, s])`

<a id="sec-4-2"></a>
### 4.2 Legacy（EIP-155）签名哈希
- 预签名消息（EIP-155）：
  `keccak256(rlp([nonce, gasPrice, gasLimit, to, value, data, chainId, 0, 0]))`
- 签名后 `v = chainId * 2 + 35/36`（取决于恢复位）。

<a id="sec-4-3"></a>
### 4.3 Type 2（EIP-1559）签名哈希
- 预签名消息：
  `keccak256(0x02 || rlp([chainId, nonce, maxPriorityFeePerGas, maxFeePerGas, gasLimit, to, value, data, accessList]))`
- 结果签名字段是 `yParity, r, s`。

<a id="sec-4-4"></a>
### 4.4 Type 3（EIP-4844）签名哈希
- 预签名消息基于 Type3 的 unsigned payload（不包含 sidecar）。
- 工程关键：签名对象与网络传播附加数据分层处理，不要混在同一抽象里。

<a id="sec-4-5"></a>
### 4.5 `v/r/s` 与 `yParity`
- Legacy 常看 `v/r/s`，typed tx 常看 `yParity/r/s`。
- 钱包端校验至少包含：
  - `r`、`s` 非零且在合法范围。
  - `s` low-s 规范化（多数库默认处理）。
  - 恢复地址与期望 `from` 一致。

## 5. Gas 与手续费计算（工程最容易踩坑）

<a id="sec-5-1"></a>
### 5.1 Intrinsic Gas（基础消耗）
常见组成（以 EVM 主网规则为主）：
- 基础交易成本：`21000`
- calldata 成本：零字节与非零字节按不同单价计费
- 合约创建额外成本（若 `to` 为空）
- access list 额外成本（Type1/2/3）

结论：`gasLimit` 不是拍脑袋给，必须估算 + buffer。

<a id="sec-5-2"></a>
### 5.2 EIP-1559 实际扣费公式
- `effectivePriorityFeePerGas = min(maxPriorityFeePerGas, maxFeePerGas - baseFee)`
- `effectiveGasPrice = baseFee + effectivePriorityFeePerGas`
- `实际执行费 = gasUsed * effectiveGasPrice`

用户“最大可能扣费上限”通常按：
- `gasLimit * maxFeePerGas`（再加 value）
做展示与余额校验。

<a id="sec-5-3"></a>
### 5.3 发送前余额检查规则
- 普通调用：`balance >= value + gasLimit * maxFeePerGas`
- Token 转账（`value=0`）：`balance >= gasLimit * maxFeePerGas`
- Blob 交易：额外考虑 blob fee 上限。

<a id="sec-5-4"></a>
### 5.4 Blob 费用（EIP-4844）详细说明
Type 3（Blob）交易里有两套费用，必须分开理解：

1. 执行费用（Execution Gas Fee）
- 和 Type2 一样，来自 EVM 执行：
  `executionFee = gasUsed * effectiveGasPrice`

2. Blob 费用（Data Gas Fee）
- 为 blob 数据空间单独付费：
  `blobFee = blobGasUsed * blobBaseFee`

核心字段：
- `maxFeePerBlobGas`：你愿意支付的 blob 单价上限
- `blobBaseFee`：当前网络 blob 基础费（协议动态调整）
- `blobVersionedHashes`：本次交易关联的 blob 引用（数量通常反映 blob 数）

关键判断：
- 如果 `maxFeePerBlobGas < blobBaseFee`，交易通常不会被打包。
- blob 成本和执行成本是两条费率曲线，不要混成一个“gasPrice”去理解。

钱包展示建议：
- 把费用拆成两行展示：
  - 执行费（Execution）
  - Blob 费（Data）
- 再给一个总上限，用户会更容易理解“为什么这笔比普通 Type2 贵”。

发送前校验建议：
- 除了 `maxFeePerGas`，还要校验 `maxFeePerBlobGas`。
- 上限预留可按下面思路估算：
  - `value`
  - `gasLimit * maxFeePerGas`
  - `blobGasUsed * maxFeePerBlobGas`

<a id="sec-6"></a>
## 6. 钱包发送交易前的校验清单
1. 网络与 `chainId` 一致。
2. `from` 账户可用且已解锁（或签名器可用）。
3. `nonce` 来自 `pending` 视图。
4. `to` 地址格式合法；合约创建场景 `to` 为空且 `data` 非空。
5. 金额单位转换正确（避免小数精度错误）。
6. `gasLimit` 已估算并加 buffer。
7. 费用参数满足链上当前拥堵情况（可基于 `eth_feeHistory`）。
8. 用户余额覆盖“上限扣费 + value”。
9. 高风险方法有二次确认（授权、升级、批量调用）。
10. 签名后做本地 recover 校验（可选但推荐）。

<a id="sec-7"></a>
## 7. RPC 映射：每个字段该怎么取
- `nonce`：`eth_getTransactionCount(address, "pending")`
- `gasLimit`：`eth_estimateGas`
- 费用建议：`eth_feeHistory` + `eth_maxPriorityFeePerGas`
- 广播：`eth_sendRawTransaction`
- 跟踪状态：`eth_getTransactionReceipt`
- 只读预检查：`eth_call`

<a id="sec-8"></a>
## 8. 常见错误与排障
- `nonce too low`
  - 原因：nonce 已被使用或本地 nonce 落后。
  - 处理：重新拉 `pending nonce`，必要时用同 nonce 替换策略。

- `replacement transaction underpriced`
  - 原因：同 nonce 替换时加价不够。
  - 处理：提高 `maxPriorityFeePerGas` 与 `maxFeePerGas`（常见至少上调约 10%）。

- `insufficient funds for gas * price + value`
  - 原因：余额不足覆盖上限成本。
  - 处理：降低 value、提高余额、或降低费用参数（在可打包前提下）。

- `intrinsic gas too low` / `out of gas`
  - 原因：`gasLimit` 偏低。
  - 处理：重新估算并增加 buffer。

<a id="sec-9"></a>
## 9. 生产级实现建议（钱包端）
- 做统一 TxBuilder：
  - 按链能力自动选择 type（默认 Type2）。
  - 统一单位与字段校验。

- 做 NonceManager：
  - 进程内锁 + 持久化。
  - 支持失败回滚与冲突恢复。

- 做 FeePolicy：
  - 慢/中/快三档推荐。
  - 拥堵时动态调参。
  - 支持 speed up / cancel。

- 做 TxTracker：
  - 维护 `localId -> txHash -> receipt` 状态机。
  - 替换交易时维护旧新 txHash 映射。

## 10. 最小可用 Type 2 示例
```json
{
  "type": "0x2",
  "chainId": "0x1",
  "nonce": "0x15",
  "to": "0x1111111111111111111111111111111111111111",
  "value": "0x0",
  "data": "0xa9059cbb000000000000000000000000222222222222222222222222222222222222222200000000000000000000000000000000000000000000000000000000000f4240",
  "gas": "0x186a0",
  "maxPriorityFeePerGas": "0x59682f00",
  "maxFeePerGas": "0x2540be400",
  "accessList": []
}
```

说明：
- 上例 `data` 是 ERC-20 `transfer(address,uint256)` 的典型编码形态。
- 实际生产中，费用参数应根据实时链上费率动态生成，而不是写死。
