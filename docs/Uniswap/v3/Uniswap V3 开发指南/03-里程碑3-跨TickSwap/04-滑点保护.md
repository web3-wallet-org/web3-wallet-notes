# 04 滑点保护

原文：<https://learnblockchain.cn/article/23803?course_id=100>

这一节讲怎么给 `swap` 和 `mint` 加保护，避免链上真实执行结果和用户预期差太远。

先记住一句话：

```text
滑点保护不是为了保证交易一定成功，而是为了防止交易在糟糕条件下成功。
```

也就是说，用户真正想表达的是：

```text
如果结果还在我能接受的范围内，就成交。
如果结果已经比我能接受的更差，就回滚。
```

## 滑点是什么

滑点就是：用户提交交易时看到的是一个结果，但交易真正上链执行时，池子的状态已经变了。

比如用户点 swap 时看到：

```text
用 1000 USDC 大约能买到 0.5 ETH
```

但从交易提交到被打包，中间有一段时间。别人可能先成交，池子的价格和流动性都会变化。

等用户的交易真正执行时，结果可能变成：

```text
1000 USDC 只能买到 0.47 ETH
```

如果用户不能接受这个结果，就应该让交易失败，而不是继续成交。

滑点保护还可以降低三明治攻击的伤害。攻击者如果能把用户交易夹在两笔自己的交易中间，就可能先把池子价格推坏，让用户用更差价格成交，再把价格推回去套利。

滑点保护不能彻底消灭这种攻击，但可以给交易设置底线：

```text
价格被推得太差时，交易直接回滚。
```

## Swap 保护的是什么

swap 保护的是成交价格。

用户不是只关心“能不能成交”，还关心：

```text
成交价格最多能坏到哪里？
```

课程里给 `swap` 增加了一个参数：

```text
sqrtPriceLimitX96
```

它表示这次 swap 最多允许价格走到哪里。

如果价格碰到这个限制，就不能继续撮合。即使用户还有输入没用完，swap 也要停下来。

## 为什么用 `sqrtPriceLimitX96`

在 Pool 层，swap 是通过不断推动价格来完成的。

上一节讲过，跨 tick swap 会一段一段执行：

```text
当前价格 -> 下一个 tick
下一个 tick -> 再下一个 tick
...
```

所以 Pool 层最自然的限制方式就是：

```text
价格最多只能走到某个边界。
```

这个边界就是 `sqrtPriceLimitX96`。

你也可能在其他 AMM 或 Router 里见过 `amountOutMin`。它表达的是“最终最少要拿到多少输出 token”。

这两个思路并不矛盾：

- `sqrtPriceLimitX96` 是 Pool 层的价格边界；
- `amountOutMin` 是 Router 或 Manager 层常见的最终输出底线。

这一节重点讲的是 Pool 层，所以用价格限制。

## 限制价格和交易方向的关系

swap 有两个方向。

如果 `zeroForOne = true`，说明用户卖 `token0` 换 `token1`，价格会往下走。

这时限制价格必须在：

```text
最小价格 < sqrtPriceLimitX96 < 当前价格
```

因为价格是往下走，用户要限制的是“最多跌到哪里”。

如果 `zeroForOne = false`，说明用户卖 `token1` 换 `token0`，价格会往上走。

这时限制价格必须在：

```text
当前价格 < sqrtPriceLimitX96 < 最大价格
```

因为价格是往上走，用户要限制的是“最多涨到哪里”。

所以滑点保护不是随便传一个价格，而是必须和交易方向匹配。

## `computeSwapStep` 怎么配合

没有滑点保护时，每一轮 swap 的目标价格通常是：

```text
下一个 tick 的价格
```

但加了 `sqrtPriceLimitX96` 以后，目标价格不能只看下一个 tick。

因为下一个 tick 可能已经超过用户允许的边界。

所以每一轮都要先选一个更保守的目标价格。

如果价格往上走：

```text
目标价格 = min(下一个 tick 价格, 用户限制价格)
```

意思是：不能涨过用户限制。

如果价格往下走：

```text
目标价格 = max(下一个 tick 价格, 用户限制价格)
```

意思是：不能跌破用户限制。

然后 `computeSwapStep` 只计算当前价格到这个目标价格之间的成交。

这样就能保证：

```text
本轮计算出来的新价格不会越过用户设置的限制。
```

## `swap` 循环怎么停止

原来的 swap 循环主要看：

```text
用户还有没有剩余输入
```

加了滑点保护后，还要多看一个条件：

```text
当前价格有没有碰到 sqrtPriceLimitX96
```

所以循环可以理解成：

```text
只要还有输入，并且价格还没到限制边界，就继续 swap。
```

一旦价格到达限制边界，就停止。

如果这时用户还有输入没被用完，也没关系。因为继续成交会让价格超过用户能接受的范围。

## Mint 保护的是什么

mint 保护的不是成交价格，而是实际添加流动性时的 token 数量和比例。

用户添加流动性前，前端会根据当前价格估算：

```text
大概要用多少 token0
大概要用多少 token1
```

但交易真正执行时，价格可能已经变了。

价格一变，同一个价格范围里需要的 token0/token1 数量也会变。用户以为自己会按某个比例添加流动性，最后实际结果可能偏差很大。

所以 mint 也要有底线：

```text
实际使用的 token 数量不能低于用户能接受的最小值。
```

## `amountDesired` 和 `amountMin`

课程里在 Manager 的 `MintParams` 里增加了几个字段：

- `amount0Desired`
- `amount1Desired`
- `amount0Min`
- `amount1Min`

`Desired` 表示用户愿意最多提供多少。

`Min` 表示用户能接受的最低实际使用数量。

可以理解成：

```text
Desired = 我准备了多少
Min     = 至少要真的用掉多少，否则说明结果偏得太离谱
```

Manager 会：

1. 读取 Pool 当前价格。
2. 根据 lower tick、upper tick 和用户输入数量计算 `liquidity`。
3. 调用 Pool 的 `mint`。
4. 检查 Pool 实际收走的 `amount0` 和 `amount1` 是否低于用户设置的最小值。
5. 如果低于最小值，就回滚。

## 为什么 mint 检查放在 Manager

课程里把 mint 的滑点检查放在 Manager，而不是 Pool。

原因是 Pool 是核心合约，应该尽量只保留必要的 AMM 状态和计算逻辑。

像下面这些更偏用户体验和调用保护：

```text
用户最多愿意提供多少 token
用户至少希望实际用掉多少 token
如果偏差太大就回滚
```

更适合放在外层 Manager。

这样 Pool 保持简单，Manager 负责把用户意图翻译成对 Pool 的安全调用。

## Swap 和 Mint 的区别

两种滑点保护可以放在一起看：

```text
swap 保护的是：
成交价格不能比用户允许的更差。

mint 保护的是：
实际添加流动性的 token 数量不能偏离用户预期太多。
```

它们的共同点是：

```text
不追求一定成功，而是防止在坏条件下成功。
```

## 人话版理解

滑点保护就是给交易加一条底线。

swap 的底线是：

```text
价格不能走过我允许的边界。
```

mint 的底线是：

```text
实际用掉的 token 数量不能低于我设置的最小值。
```

没有这条底线，交易可能成功，但结果不是用户愿意接受的结果。

## 你要记住

- 滑点保护不是保证成交，而是防止糟糕成交。
- swap 用 `sqrtPriceLimitX96` 控制价格最多能走到哪里。
- `computeSwapStep` 的目标价格不能越过用户设置的限制。
- 价格往上走时，目标价格取 `min(下一个 tick 价格, 用户限制价格)`。
- 价格往下走时，目标价格取 `max(下一个 tick 价格, 用户限制价格)`。
- mint 用 `amount0Min` 和 `amount1Min` 检查实际使用数量是否低于用户底线。
- mint 的滑点检查适合放在 Manager，而不是 Pool。
