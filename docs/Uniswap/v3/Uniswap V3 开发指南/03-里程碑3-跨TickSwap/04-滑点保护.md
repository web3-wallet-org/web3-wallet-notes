# 04 滑点保护

原文：<https://learnblockchain.cn/article/23803?course_id=100>

这一节讲怎么给 swap 和 mint 加保护，避免链上真实执行结果和用户看到的报价差太远。

## 滑点是什么

滑点就是：你点交易时看到一个价格，但交易真正上链执行时，价格已经变了。

原因很简单：你提交交易和交易被打包之间有时间差。在这段时间里，别人可以先成交，池子的价格和流动性都会变。

滑点保护还可以降低三明治攻击的伤害。攻击者如果能把你的交易夹在两笔自己的交易中间，就可能先把池子价格推坏，让你用更差价格成交，再把价格推回去套利。

## Swap 里的滑点保护

给 `swap` 增加一个参数：

```text
sqrtPriceLimitX96
```

它表示这次交易最多允许价格走到哪里。

如果 `zeroForOne = true`，说明用户卖 `token0`，价格会往下走。所以限制价格必须在当前价格和最小价格之间。

如果 `zeroForOne = false`，说明用户卖 `token1`，价格会往上走。所以限制价格必须在当前价格和最大价格之间。

swap 循环也要多一个停止条件：

```text
还有输入没成交完，并且当前价格还没碰到限制价格
```

只要价格到达 `sqrtPriceLimitX96`，就不再继续往下撮合。

## `computeSwapStep` 也要知道限制价格

每一轮本来会以“下一个 tick 的价格”为目标。但如果下一个 tick 已经超过用户允许的价格范围，就不能再拿它当目标。

所以本轮目标价格应该是：

```text
min/max(下一个 tick 价格, 用户限制价格)
```

具体取哪边，取决于交易方向。目的只有一个：这一轮计算出来的新价格不能越过用户设置的限制。

## Mint 里的滑点保护

添加流动性也有滑点问题。

用户以为自己会按某个比例存入两种 token，但等交易执行时，池子价格可能已经变了，实际需要的 token 数量也会变。

课程里把这部分逻辑放在 Manager 合约，而不是 Pool 合约。原因是 Pool 是核心合约，应该尽量只保留必要逻辑；用户体验相关的检查放在外层 Manager 更合适。

Manager 的 `MintParams` 会多带几个字段：

- `amount0Desired`
- `amount1Desired`
- `amount0Min`
- `amount1Min`

`Desired` 是用户愿意提供的数量，`Min` 是用户能接受的最低实际使用数量。

Manager 会：

1. 读取 Pool 当前价格。
2. 根据 lower tick、upper tick 和用户输入数量计算 `liquidity`。
3. 调用 Pool 的 `mint`。
4. 检查 Pool 实际收走的 `amount0` 和 `amount1` 是否小于用户的最低要求。
5. 如果小于，就回滚。

## 人话版理解

滑点保护就是给交易加一条底线。

swap 的底线是：价格不能比我允许的更差。

mint 的底线是：实际使用的 token 数量不能偏离我预期太多。

没有这条底线，交易可以成功，但结果可能不是用户愿意接受的结果。

## 你要记住

- swap 用 `sqrtPriceLimitX96` 控制价格最多能走到哪里。
- `computeSwapStep` 不能计算超过限制价格的那一段。
- mint 的滑点保护放在 Manager 里，用 `amount0Min` 和 `amount1Min` 检查。
- 滑点保护不是为了保证一定成交，而是为了防止用糟糕条件成交。
