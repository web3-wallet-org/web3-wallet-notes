# 05 实现流动性计算

原文：<https://learnblockchain.cn/article/23805?course_id=100>

这一节把“根据 token 数量和价格范围计算流动性”的逻辑搬到 Solidity 里。

先记住这条主线：

```text
用户输入的是 amount0Desired / amount1Desired。
Pool.mint 需要的是 liquidity。
Manager 的任务，就是把用户给的 token 数量换算成最多能铸造多少 liquidity。
```

## 这节在解决什么

前面我们已经会做一件事：

```text
给定 liquidity
反推出需要多少 token0 和 token1
```

现在要做反方向：

```text
给定 token0 数量、token1 数量、价格范围
算出最多能得到多少 liquidity
```

这一步是通用化 `mint` 的基础。

因为真实用户不会直接说：

```text
我要 mint 123456 liquidity
```

用户更自然的输入是：

```text
我最多愿意提供 1 ETH 和 2000 USDC
价格范围是 1800 到 2200
```

所以 Manager 要根据这些输入，算出一个合适的 `liquidity`，再调用 Pool 的 `mint`。

## 先看价格位置

计算 liquidity 前，先要看当前价格和用户价格范围的关系。

如果当前价格低于用户区间：

```text
当前价格 < lower price
```

说明这个仓位还没被激活。它在当前价格上方，开始时只需要 `token0`。

如果当前价格高于用户区间：

```text
当前价格 >= upper price
```

说明这个仓位也不在当前价格里。它在当前价格下方，开始时只需要 `token1`。

如果当前价格在用户区间内：

```text
lower price <= 当前价格 < upper price
```

说明这段流动性马上可用，需要同时提供 `token0` 和 `token1`。

所以 `getLiquidityForAmounts` 的判断逻辑，本质就是先判断价格位置，再选择对应的计算方式。

## 用 token0 计算流动性

如果只看 `token0`，流动性和价格区间的两个平方根价格有关。

可以先不用死记公式，只要记住：

```text
token0 对应的是 1 / sqrt(P) 方向的变化。
```

整理后，公式可以理解为：

```text
L = amount0 * sqrt(upper) * sqrt(lower) / (sqrt(upper) - sqrt(lower))
```

也就是说，给定一段价格范围和一笔 `token0`，可以算出这笔 `token0` 最多能支撑多少流动性。

因为 Solidity 里乘法再除法容易溢出，所以实现时要用安全的乘除函数，比如 `PRBMath.mulDiv`。

## 用 token1 计算流动性

如果只看 `token1`，公式更直接。

可以理解为：

```text
token1 对应的是 sqrt(P) 方向的变化。
```

整理后：

```text
L = amount1 / (sqrt(upper) - sqrt(lower))
```

在 Q64.96 定点数里，还要处理缩放因子，所以代码里同样会用 `mulDiv` 做安全计算。

## 为什么会算出两个 L

流动性最终只有一个 `L`，但当当前价格在用户区间内时，用户需要同时提供两种 token。

这时可以分别计算：

```text
amount0 最多能支撑多少 liquidity
amount1 最多能支撑多少 liquidity
```

问题是，用户给的两种 token 数量不一定刚好匹配当前价格需要的比例。

比如：

```text
token0 很多
token1 很少
```

那最终能铸造多少 liquidity，就会被 `token1` 限制。

反过来也一样：

```text
token1 很多
token0 很少
```

那最终能铸造多少 liquidity，就会被 `token0` 限制。

所以当前价格在区间内时，要分别用 `token0` 和 `token1` 算一次流动性，然后取较小值。

较小的那个才是这两种 token 数量共同能支撑的最大 `liquidity`。

## `getLiquidityForAmounts` 怎么选

最终函数会根据当前价格位置选择算法。

当前价格低于用户区间：

```text
只用 token0 计算 liquidity
```

当前价格高于用户区间：

```text
只用 token1 计算 liquidity
```

当前价格在用户区间内：

```text
用 token0 算一个 liquidity
用 token1 算一个 liquidity
取较小值
```

这就是 `getLiquidityForAmounts` 的核心逻辑。

## 和上一节滑点保护的关系

上一节讲的 `amount0Desired` 和 `amount1Desired`，就是这里的输入。

Manager 会先用这两个 desired 数量计算出最多能 mint 的 `liquidity`。

然后调用 Pool 的 `mint`，得到实际使用的：

```text
amount0
amount1
```

最后再检查它们是否低于：

```text
amount0Min
amount1Min
```

所以这两节是连在一起的：

```text
05 负责算：用户这些 token 能 mint 多少 liquidity。
04 负责查：实际用掉的 token 数量有没有低于用户底线。
```

## 人话版理解

这节其实就是在算：

```text
用户这些钱，最多能买到多少做市能力？
```

如果用户的价格范围还没到当前价格，只需要一种 token。

如果用户的价格范围包含当前价格，就需要两种 token 搭配。哪种 token 少，哪种 token 就决定最终能铸造多少流动性。

## 你要记住

- 用户输入的是 token 数量，Pool.mint 需要的是 `liquidity`。
- Manager 要负责把 `amount0Desired` / `amount1Desired` 换算成 `liquidity`。
- `getLiquidityForAmount0` 用 `token0` 数量算流动性。
- `getLiquidityForAmount1` 用 `token1` 数量算流动性。
- `getLiquidityForAmounts` 会根据当前价格位置选择合适算法。
- 当前价格在区间内时，必须取两个 liquidity 结果里的较小值。
