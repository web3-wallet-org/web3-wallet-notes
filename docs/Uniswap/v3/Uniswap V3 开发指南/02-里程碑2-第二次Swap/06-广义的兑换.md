# 06 广义的兑换

这一节可以先用一句话理解：

> 把 `swap` 从“写死方向、写死数量的演示代码”，升级成一个真正通用的兑换函数。

也就是说，之前的 `swap` 更像教学 Demo。  
这一节开始，它慢慢变成真实 Uniswap V3 的样子。

## 之前的问题

前面的版本为了方便理解，很多东西是写死的：

- 只能按一个方向换
- 输入数量不够灵活
- 输出数量不是完整动态计算
- 还不能为后面的跨 tick 兑换做准备

真实的 DEX 不可能这样。

用户可能会做：

```text
token0 -> token1
token1 -> token0
卖出 1 ETH
卖出 1000 USDC
```

所以 `swap` 必须变成一个通用函数。

## 新的 swap 长什么样

```solidity
swap(recipient, zeroForOne, amountSpecified, data)
```

先抓住两个参数就够了。

## zeroForOne：控制兑换方向

```text
zeroForOne = true   表示 token0 -> token1
zeroForOne = false  表示 token1 -> token0
```

假设池子是：

```text
token0 = ETH
token1 = USDC
```

那就是：

```text
true  = ETH 换 USDC
false = USDC 换 ETH
```

这个参数解决的是：

> 用户到底是卖 token0，还是卖 token1？

## amountSpecified：用户卖出多少

这一节实现的是 **exact input**。

意思是：

```text
用户先确定自己要卖多少
协议再计算用户能拿到多少
```

比如：

```text
我卖出 1 ETH
系统计算我能拿到多少 USDC
```

不是：

```text
我一定要拿到 2000 USDC
系统反推我要付多少 ETH
```

后面这种叫 **exact output**，这一节还没做。

## 为什么叫“广义的兑换”

因为现在的 `swap` 不再服务于某一个固定例子。

它开始具备三个通用能力：

- 方向可以切换
- 输入数量可以变化
- 输出数量根据当前池子状态动态计算

这就是“广义”的意思。

## swap 的本质

V3 的 swap 不是简单地做：

```text
输入数量 * 当前价格 = 输出数量
```

真正发生的是：

```text
输入 token
  -> 推动池子价格移动
  -> 根据价格移动的幅度
  -> 反推出用户能拿到多少输出 token
```

所以你要记住：

> swap 的核心不是“按当前价格乘一下”，而是“输入推动价格移动”。

## computeSwapStep：每一步算什么

`computeSwapStep` 是这一节最重要的内部函数。

它只解决一个小问题：

> 在当前价格到目标价格这一小段里，最多能吃掉多少输入，又能给出多少输出？

整个 swap 可以理解成很多个小 step 拼起来：

```text
第 1 步：从当前价格走到下一个目标价格
第 2 步：如果输入还没用完，继续走
第 3 步：再继续
...
直到用户输入被处理完
```

这一节还没有把跨 tick 做到完整复杂版，但代码结构已经开始为它铺路。

## 最小执行流程

你可以先按这个顺序理解：

```text
1. 读取当前价格和 tick
2. 判断兑换方向 zeroForOne
3. 记录用户还剩多少输入没有处理
4. 找到当前方向上的目标价格
5. 调用 computeSwapStep 计算这一小步
6. 更新价格、tick、剩余输入、累计输出
7. 如果输入还没处理完，就继续下一步
8. 最后算出 amount0 和 amount1
9. 池子先转出输出 token
10. 通过 callback 收回输入 token
```

## amount0 / amount1 的正负号

这个地方很容易绕。  
只要永远站在 **池子视角** 看就行。

```text
正数 = 池子收到
负数 = 池子付出
```

如果是 `token0 -> token1`：

```text
池子收到 token0，所以 amount0 > 0
池子付出 token1，所以 amount1 < 0
```

如果是 `token1 -> token0`：

```text
池子收到 token1，所以 amount1 > 0
池子付出 token0，所以 amount0 < 0
```

记忆方式：

> 用户卖出的，就是池子收到的，所以是正数。

## 为什么池子可以先转出 token

V3 的 `swap` 不是一上来就让用户先付款。

它的流程是：

```text
池子先把输出 token 转给用户
然后调用 callback
要求调用方把输入 token 付回来
最后检查余额是否真的到账
```

如果 callback 后余额不对，交易会直接 `revert`。

由于 EVM 交易有原子性，`revert` 后前面转出的 token 也会一起撤销。

所以安全性靠的是：

> callback 后的余额检查 + 交易原子性

不是靠信任用户。

## 这一节你真正要带走什么

这节不用死磕每个数学细节，先抓住这几个点：

- `zeroForOne` 控制兑换方向。
- `amountSpecified` 表示用户卖出多少，这是 exact input。
- V3 的 swap 是“输入推动价格移动”，不是简单乘当前价格。
- `computeSwapStep` 负责计算每一小段价格移动。
- `amount0/amount1` 的正负号永远按池子视角理解。
- callback + 余额检查保证池子不会白白转出 token。

一句话总结：

> 这一节是在把 swap 从“教学示例”改造成“真实 DEX 需要的通用兑换框架”。
