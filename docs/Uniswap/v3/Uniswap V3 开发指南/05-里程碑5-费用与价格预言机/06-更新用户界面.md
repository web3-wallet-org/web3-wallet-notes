# 06 更新用户界面

原文：<https://learnblockchain.cn/article/23819?course_id=100>

这一节的重点不是做一个完整的行情页，也不是重新讲价格预言机。

它要解决的是一个更直接的问题：

```text
前面合约已经支持 burn 和 collect。
现在前端也要让 LP 用户能查看仓位、移除流动性、领取 token。
```

也就是说，用户界面要从“只能添加流动性”，升级成“可以管理自己的 LP 仓位”。

## 先看完整流程

用户想移除流动性时，前端大概要做这些事：

```text
1. 用户选择价格范围
2. 前端把价格范围转换成 lowerTick / upperTick
3. 前端读取用户在这个范围里的仓位
4. 用户输入要移除的流动性数量
5. 前端算出对应的 Pool 地址
6. 前端调用 pool.burn(...) 释放流动性
7. 前端从 Burn 事件里拿到 amount0 / amount1
8. 前端调用 pool.collect(...) 把 token 转回用户钱包
```

后面的内容，都是在解释这个流程里的几个关键点。

## 第一步：先读取用户仓位

用户要移除流动性，前端必须先知道用户有多少流动性可以移除。

在 Uniswap V3 里，一个仓位不是只看用户地址就能确定的。它由这些信息共同决定：

```text
owner
lowerTick
upperTick
Pool
```

也就是说，同一个用户可以在不同价格范围里有不同仓位。

课程里为了让前端少处理一些底层细节，在 Manager 里加了 `getPosition` 辅助函数。前端调用它后，可以拿到：

```text
liquidity
feeGrowthInside0LastX128
feeGrowthInside1LastX128
tokensOwed0
tokensOwed1
```

前端最直接用到的是 `liquidity`。

因为它决定了：

```text
这个用户最多能移除多少流动性。
```

## 第二步：把价格范围变成 tick

用户界面里一般不会直接让用户输入 tick。

用户更容易理解的是价格范围，比如：

```text
最低价格
最高价格
```

但合约里记录仓位时，用的是 tick 范围：

```text
lowerTick
upperTick
```

所以前端要把用户输入的价格转换成 tick，然后再用 `nearestUsableTick` 按 `tickSpacing` 对齐。

这一步的结果会影响两个地方：

- 读取仓位时，要用这个 tick 范围查用户的 position。
- 移除流动性时，也要把同一组 tick 传给 `burn` 和 `collect`。

## 第三步：算出 Pool 地址

读取仓位可以通过 Manager 的 `getPosition` 辅助函数完成。

但课程里的移除流动性和领取 token，是直接调用 Pool：

```text
pool.burn(...)
pool.collect(...)
```

所以前端必须知道目标 Pool 的地址。

上一章已经用 `CREATE2` 让 Pool 地址可以按规则计算出来。前端可以通过这些信息算出 Pool 地址：

```text
factory 地址
token0
token1
fee 或 tickSpacing
poolCodeHash
```

真实 Uniswap V3 通常用 `fee` 区分不同 Pool。

课程版本为了简化实现，前面一直使用的是 `tickSpacing`。

这和合约里的 `PoolAddress.computeAddress` 是同一个思路，只是把计算过程搬到了 JavaScript 里。

## poolCodeHash 是什么

`CREATE2` 计算地址时，需要知道 Pool 创建代码的摘要 hash。

你可以把它理解成：

```text
这份 Pool 部署代码的指纹。
```

前端不需要保存完整的 Pool 部署代码，只需要提前用 Foundry 算出 `poolCodeHash`，然后把它作为常量写进前端。

这里最重要的是：

```text
poolCodeHash 必须和实际部署的 Pool 创建代码一致。
```

如果 Pool 创建代码变了，`poolCodeHash` 也要更新。

否则前端算出来的 Pool 地址会错，后续调用 `burn` 和 `collect` 时就会找错合约。

## 第四步：调用 burn 释放流动性

用户输入要移除的流动性数量后，前端调用：

```text
pool.burn(lowerTick, upperTick, amount)
```

这里的 `amount` 是要移除的 liquidity 数量。

`burn` 做两件事：

```text
1. 减少用户在这个价格范围里的流动性
2. 计算这次移除流动性能拿回多少 token0 / token1
```

但要注意，`burn` 不等于直接把 token 转给用户。

它更像是让合约先完成结算。

## 第五步：调用 collect 领取 token

`burn` 成功后，会通过 Burn 事件告诉前端这次释放了多少：

```text
amount0
amount1
```

前端拿到这两个数后，再调用：

```text
collect(account, lowerTick, upperTick, amount0Burned, amount1Burned)
```

这一步才是真正把 token 转回用户钱包。

所以这一节里最关键的关系是：

```text
burn    = 释放流动性并结算数量
collect = 把结算出来的 token 转给用户
```

如果实际应用里还想顺便领取手续费，就要更完整地处理 `tokensOwed0` 和 `tokensOwed1`。

课程这里主要是先把“移除流动性并取回 token”这条流程跑通。

## 人话版理解

前端以前像一个只能“存钱”的页面：

```text
swap
mint liquidity
```

这一节要把它补成一个真正的 LP 管理页面：

```text
先查你存了多少
再让你选择取多少
取出时先让合约结算
最后把钱转回钱包
```

`burn` 像把定期存款解冻。

`collect` 像把解冻后的钱转到银行卡。

## 你要记住

- UI 现在要支持读取仓位、移除流动性、领取 token。
- 仓位由 owner、lowerTick、upperTick 和 Pool 共同决定。
- Manager 的 `getPosition` 是为了让前端少处理一些底层细节。
- 用户输入的价格范围，最终会转换成 lowerTick / upperTick。
- 前端仍然需要根据 `CREATE2` 规则计算 Pool 地址。
- `poolCodeHash` 必须和实际部署的 Pool 创建代码匹配。
- `burn` 负责释放和结算，`collect` 负责转账。

- 用户界面里的价格范围，为什么最终要变成 lowerTick / upperTick？
- 前端为什么还需要计算 Pool 地址？
- `poolCodeHash` 如果错了会发生什么？
- 为什么调用 `burn` 后还要调用 `collect`？
