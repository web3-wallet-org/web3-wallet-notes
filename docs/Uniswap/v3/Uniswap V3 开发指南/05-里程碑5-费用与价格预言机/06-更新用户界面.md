# 06 更新用户界面

原文：<https://learnblockchain.cn/article/23819?course_id=100>

这一节把第 5 章新增的能力接到前端。

核心是：

```text
用户现在不只要添加流动性，还要能查看仓位、移除流动性、收取费用。
```

前面合约已经支持 `burn` 和 `collect`，前端就要给用户入口。

## 这节在解决什么

以前用户界面主要做两件事：

```text
swap
mint liquidity
```

现在 LP 需要管理自己的仓位：

```text
我这个价格范围里有多少流动性？
我能移除多少？
移除后能拿回多少 token？
我赚到的费用能不能领取？
```

所以前端要补仓位读取和移除流程。

## 为什么先获取仓位

用户要移除流动性，首先得知道自己有多少流动性。

仓位的 key 由三部分组成：

```text
owner
lowerTick
upperTick
```

还要知道对应 Pool。

这些在前端手动拼会比较麻烦，所以课程在 Manager 里加了 `getPosition` 辅助函数。

它帮前端返回：

```text
liquidity
feeGrowthInside0LastX128
feeGrowthInside1LastX128
tokensOwed0
tokensOwed1
```

前端最直接用的是 `liquidity`，因为它决定用户最多能移除多少。

## 为什么还要算 Pool 地址

读取仓位可以走 Manager 的辅助函数。

但移除流动性和收取 token，课程里是直接调用 Pool：

```text
pool.burn(...)
pool.collect(...)
```

所以前端还要知道 Pool 地址。

上一章已经用 `CREATE2` 让 Pool 地址可预测。

前端可以通过：

```text
factory 地址
token0
token1
fee
poolCodeHash
```

算出 Pool 地址。

这和合约里的 `PoolAddress.computeAddress` 是同一个思想，只是搬到 JavaScript 里。

## poolCodeHash 为什么要硬编码

`CREATE2` 计算地址需要合约 bytecode 的 hash。

前端不想把完整 Pool bytecode 放进代码里，所以会提前用 Foundry 算出：

```text
poolCodeHash
```

然后作为常量写进前端。

这个值必须和实际部署的 Pool 合约代码一致。

如果合约代码变了，code hash 也要更新。否则前端算出来的 Pool 地址会错。

## 移除流动性的前端流程

用户输入价格范围和要移除的流动性数量。

前端流程大概是：

```text
1. 把价格转成 tick
2. 用 nearestUsableTick 对齐 tickSpacing
3. 算出 Pool 地址
4. 调用 pool.burn(lowerTick, upperTick, amount)
5. 从 Burn 事件里拿到 amount0 / amount1
6. 调用 pool.collect(...) 把 token 取回用户钱包
```

这里要注意：

```text
burn 只是结算和释放流动性，不一定直接把 token 打给用户。
collect 才是真正转账。
```

所以前端通常会在 burn 成功后马上 collect。

## 为什么 burn 后要读事件

`burn` 会告诉你这次释放了多少 `amount0` 和 `amount1`。

前端拿到这两个数后，再传给 `collect`：

```text
collect(account, lowerTick, upperTick, amount0Burned, amount1Burned)
```

这样用户移除多少，就领取多少。

如果想顺便领取费用，实际应用里还会更完整地处理 `tokensOwed`。

课程这里主要是把“移除流动性并领取释放 token”这条路跑通。

## 人话版理解

前端以前像一个只会“存钱”的页面。

这一节要补成真正的 LP 管理页面：

```text
先查你存了多少
再让你选择取多少
取出时先让合约结算
最后把钱转回钱包
```

`burn` 像把定期存款解冻，`collect` 像把解冻后的钱转到银行卡。

## 你要记住

- UI 现在要支持读取仓位、移除流动性、收取 token。
- 仓位由 owner、lowerTick、upperTick 和 Pool 共同决定。
- Manager 的 `getPosition` 是为了让前端少算一些底层细节。
- 前端仍然需要根据 `CREATE2` 规则计算 Pool 地址。
- `poolCodeHash` 必须和实际 Pool bytecode 匹配。
- `burn` 负责释放和结算，`collect` 负责转账。
