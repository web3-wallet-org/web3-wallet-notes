# 05 价格预言机

原文：<https://learnblockchain.cn/article/23816?course_id=100>

## 一句话

```text
Pool 自己记录历史价格，外部合约直接读 Pool 就能拿到一段时间的平均价，
不需要任何人从链下搬数据上来。
```

## 这节在解决什么

很多链上协议需要价格，比如借贷协议清算时要知道"ETH 现在值多少 USDC？"

有三种方式获取价格：

| 方式 | 原理 | 问题 |
|---|---|---|
| 币安 API | 自己读，自己写进合约 | 信任搬运工一个人，生产环境不能用 |
| Chainlink | 多个节点聚合外部价格后喂到链上 | 依赖外部网络，需要付费 |
| Uniswap TWAP | Pool 自己的交易价格就是数据源 | 池子太浅时容易被操纵 |

Uniswap 的思路最简单：**交易本身就是链上发生的，为什么还要从链下搬价格？** Pool 直接记录自己的成交历史，谁需要价格就来读。

但它不是万能的——池子流动性越深、套利越充分，价格越可靠。长尾资产的浅池子，还是得用 Chainlink。

## 用哪个价格？

**当前价格（slot0.sqrtPriceX96）**：一秒就能读到，但一笔大单就能推歪。不适合做清算判断、资产计价这种"被操纵能赚钱"的场景。

**时间加权平均价格（TWAP）**：读一段时间的均值，操纵需要持续砸钱，成本高得多。这才是协议真正用的价格。

## 对外接口长什么样

Uniswap V3 只暴露一个查询函数：

```solidity
pool.observe(secondsAgos);
```

传入一组"往回多少秒"的时间点，返回每个时间点对应的 `tickCumulative`（tick 历史累积值）。

比如查过去 30 分钟的平均价：

```solidity
// 30分钟前 和 现在
(uint56[] memory tickCumulatives, ) = pool.observe([30 * 60, 0]);
```

拿到两个累积值后，自己算价格：

```text
平均 tick = (tickCumulatives[1] - tickCumulatives[0]) ÷ 1800秒
TWAP 价格 = 1.0001 ^ 平均 tick
```

对调用者来说，接口就这么简单。下面全是这个接口背后的实现细节。

## 为什么记录 tick 累积值而不是直接记价格

V3 里价格和 tick 的关系：

```text
价格 = 1.0001 ^ tick
```

预言机存的是 **tick 累积值**（tickCumulative），不是价格，也不是每秒的 tick 快照。

累积方式：

```text
新累积值 = 上一次累积值 + 当前 tick × 时间间隔
```

比如 tick = 200 持续了 10 秒，就加 200 × 10 = 2000。

这样存有两个好处：
1. **时间加权自动算好**——tick 在哪个值停得越久，对累积值的贡献越大
2. **存储节省**——只存一个累积值，不需要存每一秒的数据

## TWAP 的公式

有了两个时间点的累积值：

```text
平均 tick = (tickCumulative_t2 - tickCumulative_t1) ÷ (t2 - t1)
平均价格 = 1.0001 ^ 平均 tick
```

和算平均车速完全一样——拿终点里程减起点里程，除以时间。

## Observation 是什么

`Observation` 是历史记录槽，每次写入存两个数据：

```text
timestamp        — 这条记录什么时候写的
tickCumulative   — 当时的累积值
```

Pool 里有一个固定长度的 observation 数组。

## cardinality：决定了你能查多久以前

要算"过去 30 分钟 TWAP"，得有 30 分钟前的 tickCumulative。

但 observation 数组是固定长度，满了就覆盖最老的：

```text
10 个槽位，每 1 分钟写一条 → 最早 10 分钟前 → 算不了 30 分钟 TWAP ❌
100 个槽位，每 1 分钟写一条 → 最早 100 分钟前 → 算得了 30 分钟 TWAP ✓
```

所以 `cardinality` 就是槽位数量，**越大能回溯的时间越长**。

那为什么不默认开很大？因为每个槽位初始化和写入都要 gas。普通 swap 用户不需要查历史，没理由替别人付这个钱。谁需要更长历史（比如借贷协议），谁自己调大容量、自己付 gas。

## 同一个区块为什么只写一次

一个区块里可能发生多笔 swap，但它们共享同一个 `block.timestamp`。既然时间戳一样，写一次和写十次的 tickCumulative 没区别，重复写纯属浪费 gas。

所以 Pool 的规则是：这个区块如果已经写过一次 observation，本区块内后续 swap 全部跳过，不写了。

## 读取为什么复杂（先知道有这事就行）

observation 数组是环形缓冲区——满了新记录覆盖最老的。另外不是每个区块都有观察值（有些区块没有 swap）。

所以读取时要处理：

```text
找到目标时间点前后的观察值
如果刚好没有，插值
如果数组绕了一圈，正确处理顺序
```

涉及二分搜索。但目前只需要知道目标：**拿到某个时间点对应的 tickCumulative**。具体算法后面再扣。

## 和 Chainlink 怎么选

| 场景 | 用哪个 |
|---|---|
| Pool 流动性深、主流币对（ETH/USDC） | Uniswap TWAP，纯链上，零外部依赖 |
| 长尾资产、浅池子 | Chainlink，采多交易所聚合价，不受单一池子深度影响 |
| 生产级协议 | 两者搭配——TWAP 做主价，Chainlink 做校验或兜底 |
| 测试/PoC | 币安 API 直接读就行 |

## 人话版理解

价格预言机就是给 Pool 装了个行车记录仪。

它不每秒拍照，而是存**里程表读数**（tickCumulative）。想算过去 30 分钟的平均速度（均价），就用现在里程减 30 分钟前里程，除以时间。

接口就是一个 `observe()`，复杂度全藏在后面——环形数组、cardinality、二分搜索——调用者不用管。

## 你要记住

- 协议用 TWAP 而不是瞬时价格，是因为瞬时价格太容易被操纵。
- Uniswap 预言机的数据源是 Pool 自己的成交历史，不需要外部喂价。
- `pool.observe(secondsAgos)` 是对外唯一接口，返回 tickCumulative，剩下的自己算。
- `tickCumulative` = 当前 tick × 持续时间的累加，时间加权靠它实现。
- `Observation` 存 `timestamp` 和 `tickCumulative`，数组是环形缓冲区。
- `cardinality` 是槽位数量，决定最大回溯时长。扩容需要 gas，谁需要谁付。
- 同一区块只写一次 observation，因为时间戳一样，多写没意义。
- Chainlink 和 TWAP 互补，不是互斥。
