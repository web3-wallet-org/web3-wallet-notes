# 04 多池交易

原文：<https://learnblockchain.cn/article/23810?course_id=100>

这一节是第 4 章的核心：真正把多 Pool swap 跑起来。

先记住最重要的一句话：

<span style="color: red; font-weight: 600;">多池交易不是改 Pool，而是在 Manager 里按 Path 连续调用多个 Pool。</span>

Pool 还是只做一件事：处理自己这一对 token 的 swap。

Manager 才是把多个 Pool 串起来的人。

## 这节在解决什么

以前 Manager 的 `swap` 只支持单池交易。

大致模型是：

```text
用户给一个 Pool 地址
Manager 调这个 Pool.swap
Pool 回调 Manager 收钱
交易结束
```

现在要支持：

```text
用户给一条 Path
Manager 调第一个 Pool
第一个 Pool 输出给 Manager
Manager 拿输出再调第二个 Pool
第二个 Pool 输出给 Manager
...
最后一个 Pool 输出给用户
```

也就是说，Manager 临时变成中间 token 的接力站。

## 为什么不改 Pool

因为 Pool 是底层核心合约。

它应该只关心：

```text
当前池子里，输入多少 token，输出多少 token，价格怎么变
```

它不应该关心：

```text
用户最终要换成什么 token
后面还有几个池子
路径怎么找
哪个中间 token 接着换
```

这些属于上层组合逻辑，应该放在 Manager 和 Quoter 里。

这样分工更干净：

```text
Pool：单池数学
Manager：真实执行交易
Quoter：模拟报价
Path：描述路线
```

## 单池和多池参数的区别

单池交易用 `SwapSingleParams`。

它需要：

```text
tokenIn
tokenOut
tickSpacing
amountIn
sqrtPriceLimitX96
```

这和前面的单池 swap 很像，只是不用再传 Pool 地址，因为可以算出来。

多池交易用 `SwapParams`。

它需要：

```text
path
recipient
amountIn
minAmountOut
```

关键变化是：多池交易不用 `sqrtPriceLimitX96` 做滑点保护，而是用 `minAmountOut`。

## 为什么多池不用 sqrtPriceLimitX96

`sqrtPriceLimitX96` 是单个 Pool 内部的价格边界。

但多池交易会经过多个 Pool，每个 Pool 都有自己的价格、tick、流动性状态。

如果只给一个 `sqrtPriceLimitX96`，它到底限制哪个 Pool？

所以多池交易更自然的保护方式是：

```text
最终拿到的输出不能少于 minAmountOut
```

也就是：

```text
中间你怎么走都可以，但最后给我的数量不能低于底线。
```

## `_swap` 是什么

`_swap` 是内部复用函数。

无论单池还是多池，最终都要调用某个 Pool 的 `swap`。所以 Manager 把公共逻辑抽出来：

1. 从路径里解码出当前 Pool 参数。
2. 根据 token 地址判断 `zeroForOne`。
3. 用 `PoolAddress` 算出 Pool 地址。
4. 调用 `Pool.swap`。
5. 根据返回的 `amount0` / `amount1` 算出输出数量。

这让 `swapSingle` 和多池 `swap` 都能复用同一套底层流程。

## 多池交易怎么循环

多池交易的循环可以理解成：

```text
amountIn = 用户输入
payer = 用户

while 路径还没结束:
    取出当前第一段 Pool
    用 amountIn 去当前 Pool 交易
    得到 amountOut
    amountIn = amountOut

    如果后面还有 Pool:
        当前输出先给 Manager
        payer = Manager
        路径跳到下一段
    否则:
        最终输出给用户
        结束
```

第一跳由用户付钱。

中间跳由 Manager 付钱，因为中间 token 已经暂存在 Manager 里。

最后一跳直接把目标 token 发给用户。

## 回调里为什么要区分 payer

Pool 的 swap 会回调 Manager，让 Manager 把输入 token 转给 Pool。

但多池交易里，输入 token 的来源会变：

第一段：

```text
payer = 用户
```

Manager 要从用户钱包里 `transferFrom`。

第二段以后：

```text
payer = Manager
```

因为上一段 Pool 已经把中间 token 打给 Manager 了，所以 Manager 直接从自己的余额转给下一个 Pool。

这个 `payer` 切换，是多池交易能串起来的关键。

## Quoter 也要同步升级

真实交易前，前端需要先报价。

所以 Quoter 也要支持两类报价：

```text
quoteSingle：单池报价
quote：多池报价
```

多池报价和多池 swap 的流程类似：

1. 取路径第一段。
2. 对当前 Pool 做一次报价。
3. 把输出作为下一段输入。
4. 继续直到路径结束。

区别是 Quoter 不是真的转账，而是模拟执行，收集每一段交易后的价格和 tick。

## 人话版理解

多池 swap 像接力跑。

用户只给第一棒：

```text
WETH
```

第一个池跑完，交给 Manager：

```text
USDC
```

Manager 拿着 USDC 去第二个池，换成：

```text
USDT
```

再拿 USDT 去第三个池，最后换成：

```text
WBTC
```

最后一棒才交给用户。

Manager 的职责就是保证接力棒不要丢，并且最后结果不能低于用户设置的底线。

## 你要记住

- 多池交易逻辑放在 Manager，不放在 Pool。
- Pool 永远只处理当前池子的单次 swap。
- 多池交易的滑点保护通常看最终输出：`minAmountOut`。
- 第一跳由用户付款，后续跳由 Manager 用中间 token 付款。
- 每一跳的输出会成为下一跳的输入。
- Quoter 要按同样路径模拟多次报价。
