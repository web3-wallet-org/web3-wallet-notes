# 02 工厂合约

原文：<https://learnblockchain.cn/article/23808?course_id=100>

这一节的主角是 `Factory`。

先用一句话理解：

```text
Factory 是 Pool 的登记处、部署器，也是“按规则计算 Pool 地址”的地方。
```

前面我们创建 Pool 的方式比较直接：想用哪个 Pool，就部署哪个 Pool，然后把地址传来传去。

但一旦进入多 Pool 世界，这种方式就不够用了。因为系统里会有很多 Pool，Manager、Quoter、前端都需要知道：

```text
某两个 token 对应的 Pool 在哪里？
```

这就是 Factory 要解决的问题。

## 这节在解决什么

多池交易要求系统能快速找到 Pool。

例如路径里写着：

```text
WETH -> USDC
```

Manager 不能靠用户手动传一个 Pool 地址。更好的方式是：

```text
给我两个 token 和 tickSpacing，我先排序成 token0/token1，再自己算出 Pool 地址。
```

Factory 就是为了做到这件事。

## Factory 有三个作用

第一，Factory 是 Pool 注册表。

它会记录哪些 Pool 已经创建过：

```text
token0 + token1 + tickSpacing -> pool address
```

第二，Factory 负责部署 Pool。

以后创建 Pool 不再是随便 new 一个合约，而是统一通过 Factory。

第三，Factory 让 Pool 地址可以按规则算出来。

只要知道：

```text
factory 地址
token0
token1
tickSpacing
Pool 创建代码的摘要 hash
```

这里的 hash 可以先理解成“这份 Pool 部署代码的指纹”，不是 `.sol` 源码本身。

就可以提前算出 Pool 地址，不一定要靠别人告诉你地址，也不一定要去链上查映射。

这句话的重点是：

```text
找 Pool，从“别人告诉我地址”，变成“我按规则自己算地址”。
```

比如路径里有：

```text
WETH -> USDC -> USDT
```

Manager 可以自己算：

```text
WETH + USDC + tickSpacing -> 第一个 Pool 地址
USDC + USDT + tickSpacing -> 第二个 Pool 地址
```

然后再一段一段调用这些 Pool。

## CREATE 和 CREATE2 的区别

这节讲了 `CREATE` 和 `CREATE2`。

人话版区别是：

```text
CREATE 生成的地址和部署者 nonce 有关，不方便提前算。
CREATE2 生成的地址和 salt、部署者、合约代码有关，可以提前算。
```

`CREATE2` 的意义不是更酷，而是让地址可以提前算出来。

对 Uniswap 这种系统来说，这很重要。因为 Router、Manager、Quoter 经常需要根据 token 对找到 Pool。如果 Pool 地址能直接算出来，就不用每次查注册表。

## tickSpacing 为什么也放进 Pool 身份里

以前我们可能觉得一个 Pool 只由两个 token 决定：

```text
WETH/USDC
```

这一节开始要修正这个理解。

在这个课程版本里，Pool 身份是：

```text
token0 + token1 + tickSpacing
```

因为同一对 token 可以有不同精度的池。

比如稳定币之间价格波动小，需要更细的 tick 间距；波动大的资产可以用更粗的 tick 间距，减少跨 tick 时的 gas 成本。

注意，真实 Uniswap V3 里更常见的说法是：

```text
token0 + token1 + fee
```

`tickSpacing` 通常由手续费档位决定。课程这里直接把 `tickSpacing` 放进 Pool 身份里，是为了简化实现，让我们先把多 Pool 结构跑通。

所以：

```text
WETH/USDC + tickSpacing 60
```

和：

```text
WETH/USDC + tickSpacing 10
```

可以是两个不同的 Pool。

## tickSpacing 的人话理解

tickSpacing 就是允许初始化 tick 的步长。

如果 `tickSpacing = 60`，那可用的边界 tick 只能是：

```text
..., -120, -60, 0, 60, 120, ...
```

不能随便用 `7`、`13`、`82` 这种 tick 做流动性边界。

它的权衡是：

```text
tickSpacing 小：价格范围更精细，但可能更费 gas
tickSpacing 大：价格范围更粗糙，但跨 tick 搜索更省 gas
```

注意：当前价格本身仍然可以很精细，`tickSpacing` 限制的是流动性区间的边界，不是每次成交后的真实价格。

## token 为什么要排序

Factory 创建 Pool 前会先把两个 token 排序：

```text
地址小的作为 token0
地址大的作为 token1
```

这是为了让同一对 token 不会创建出两个 Pool。

如果不排序，下面两个输入就可能被当成不同的池：

```text
WETH, USDC
USDC, WETH
```

排序之后，它们都会归一化成同一种顺序。这样 salt 一致，Pool 地址也一致。

## Pool 参数怎么传给 Pool 构造函数

这里有一个看起来有点绕的设计：

1. Factory 先把 Pool 参数暂存在 `parameters` 里。
2. Factory 用 `CREATE2` 部署 Pool。
3. Pool 构造函数反过来问 Factory：我的参数是什么？
4. Factory 部署完后删除临时参数。

这叫控制反转，也就是 Pool 构造时主动从 Factory 取参数。

人话版就是：

```text
Factory 先把出生证明放桌上。
Pool 出生时自己去桌上拿。
拿完以后 Factory 把桌子清空。
```

这样 Pool 构造函数不需要接一堆参数，同时又能拿到 `factory`、`token0`、`token1`、`tickSpacing`。

## Pool 为什么要单独 initialize

这一节还把 Pool 初始化价格从构造函数里拿出来，变成单独的 `initialize`。

原因是 Factory 只负责创建 Pool，不一定应该在构造函数里把初始价格也固定进去。

现在流程变成：

```text
Factory.createPool(...)
Pool.initialize(sqrtPriceX96)
```

`initialize` 只能调用一次，用来设置初始价格和初始 tick。

## PoolAddress 库是干什么的

`PoolAddress` 的作用是：

```text
在不查询 Factory 的情况下，根据参数直接算出 Pool 地址。
```

这对 Manager、Quoter 很关键。

但要注意：它算出来的是“如果这个 Pool 存在，它应该在哪个地址”，不等于确认这个 Pool 已经被创建。是否真的存在，仍然要看链上代码或 Factory 的记录。

以前它们可能需要用户传 Pool 地址。现在它们只需要：

```text
tokenIn
tokenOut
tickSpacing
factory
```

然后自己算出 Pool 地址。

## 你要记住

- Factory 是 Pool 的统一入口。
- 在课程版本里，Pool 的唯一身份是 `token0 + token1 + tickSpacing`；真实 V3 里通常是 `token0 + token1 + fee`。
- token 必须排序，否则同一对 token 会出现地址不一致的问题。
- `CREATE2` 让 Pool 地址可以提前计算。
- `tickSpacing` 是精度和 gas 之间的权衡。
- Pool 初始化价格从构造函数拆到了 `initialize`。
- Manager 和 Quoter 以后不需要用户手动传 Pool 地址。
