# 第05章 钱包（Web3开发者精简版）

> 状态：已完成（优化版）
> 目标：掌握钱包本质、助记词机制、HD 钱包派生、安全备份策略、账户抽象趋势

## 一句话版

钱包不是"装币的地方"，而是"**装密钥并帮你签名交易的工具**"；谁控制私钥，谁就控制链上资产。

## 核心概念速览

### 钱包的本质

| 误解 | 真相 |
|------|------|
| "我钱包里有 2 ETH" | ❌ 币在链上，不在钱包里 |
| "钱包是保险柜" | ❌ 钱包是钥匙串 |
| "钱包管资产" | ✅ 钱包管**密钥**，资产记录在区块链上 |

**正确理解**：
```
区块链（分布式账本）
  ↓ 记录
地址: 0x742d35Cc... → 余额: 2 ETH

你的钱包
  ↓ 持有
私钥: 0x... → 能控制上述地址的资产
```

## 钱包类型演进

### 非确定性钱包（JBOK）- ❌ 已淘汰

| 特性 | 说明 | 问题 |
|------|------|------|
| **生成方式** | 每个私钥独立随机生成 | 新增地址就要多备份一次 |
| **备份复杂度** | O(N)，N 为地址数量 | 容易遗漏，容错差 |
| **恢复难度** | 需要备份所有私钥 | 不适合长期使用 |

**结论**：能不用 JBOK 就别用，优先 HD 钱包体系。

### 确定性钱包（HD 钱包）- ✅ 当前主流

| 特性 | 说明 | 优势 |
|------|------|------|
| **生成方式** | 从一个种子派生所有密钥 | 只需备份一次种子 |
| **备份复杂度** | O(1)，无论多少地址 | 简单可靠 |
| **恢复能力** | 一个种子恢复全部地址 | 灾难恢复友好 |

## 助记词、种子、私钥：三层关系

### 层级结构

```
助记词（12/24 个单词）
  ↓ BIP-39 转换
种子（512 位大整数）
  ↓ BIP-32 派生
主私钥 + 链码
  ↓ 继续派生
私钥集合（m/44'/60'/0'/0/0, m/44'/60'/0'/0/1, ...）
```

### 详细对照表

| 层级 | 形式 | 长度 | 用途 | 安全级别 |
|------|------|------|------|----------|
| **助记词** | 英文单词（如 `apple banana cat ...`） | 12/15/18/21/24 词 | 人类可读备份 | ⭐⭐⭐⭐⭐ |
| **种子** | 十六进制大整数 | 512 位（64 字节） | 机器处理，派生密钥 | ⭐⭐⭐⭐⭐ |
| **私钥** | 十六进制字符串 | 256 位（32 字节） | 签名交易 | ⭐⭐⭐⭐⭐ |

**关键认知**：
- 助记词丢了 = 恢复困难（除非有其他备份）
- 助记词泄露 = 资产可能被瞬间转走
- 一个助记词可以管理**无限个地址**（通过派生路径）

---

## BIP-39：助记词标准

### 核心流程

```mermaid
graph LR
    A[128-256 位熵] --> B[添加校验和]
    B --> C[分割为 11 位组]
    C --> D[查单词表映射]
    D --> E[12-24 个助记词]
    E --> F[PBKDF2 衍生种子]
```

### 为什么用助记词

| 优势 | 说明 |
|------|------|
| **易抄写** | 单词比十六进制串更不容易出错 |
| **跨钱包兼容** | BIP-39 是通用标准，钱包间可迁移 |
| **容错设计** | 单词表经过精心设计，避免相似词混淆 |
| **校验机制** | 最后一词包含校验和，可检测输入错误 |

### 单词表规则

- 标准单词表：2048 个英文单词
- 每个词对应 11 位二进制
- 12 词 = 132 位（128 位熵 + 4 位校验）
- 24 词 = 264 位（256 位熵 + 8 位校验）

## 可选密码短语（Passphrase）

### 工作原理

```
助记词 + 空密码短语 → 种子 A → 主钱包
助记词 + "mysecret" → 种子 B → 隐藏钱包
助记词 + "other" → 种子 C → 另一个隐藏钱包
```

### 优点

| 优点 | 说明 |
|------|------|
| **隐匿钱包** | 同一助记词可生成多个独立钱包 |
| **胁迫保护** | 被胁迫时可交出无密码短语的钱包 |
| **额外安全层** | 即使助记词泄露，没密码短语也无法访问主资产 |

### 风险

| 风险 | 说明 |
|------|------|
| **遗忘风险** | 忘了密码短语 = 资产永久丢失 |
| **复杂度** | 增加了一层需要记忆的密钥 |
| **无恢复途径** | 密码短语没有备份机制（故意设计） |

**建议**：
- 大额资产可考虑使用 Passphrase
- 必须将 Passphrase 也安全备份（与助记词分开存放）
- 定期演练恢复流程

## HD 钱包（BIP-32/44）：派生路径详解

### 标准路径格式

```
m / purpose' / coin_type' / account' / change / address_index
```

### 以太坊常见路径

| 路径 | 说明 | 用途 |
|------|------|------|
| `m/44'/60'/0'/0/0` | 第一个外部地址 | 主收款地址 |
| `m/44'/60'/0'/0/1` | 第二个外部地址 | 备用地址 |
| `m/44'/60'/0'/1/0` | 第一个找零地址 | 内部使用 |
| `m/44'/60'/1'/0/0` | 第二个账户 | 多账户管理 |

### 路径组成说明

| 层级 | 名称 | 说明 | 例子 |
|------|------|------|------|
| `m` | 主密钥 | 从种子派生的根 | - |
| `purpose'` | 用途 | 固定为 44'（BIP-44） | 44' |
| `coin_type'` | 币种 | 60' = 以太坊 | 60' |
| `account'` | 账户 | 区分不同账户 | 0', 1', 2' |
| `change` | 外部/内部 | 0 = 外部（收款），1 = 内部（找零） | 0, 1 |
| `address_index` | 地址索引 | 第几个地址 | 0, 1, 2, ... |

**注意**：
- 带 `'` 的层是**强化派生**（更安全隔离）
- 路径不同 = 导出地址完全不同
- 一个助记词可以管理**多账户、多链**

## 扩展公钥（xpub）

### 什么是 xpub

扩展公钥（Extended Public Key）可以在**不暴露私钥**的前提下批量生成收款地址。

### 使用场景

| 场景 | 说明 | 安全性 |
|------|------|--------|
| **商户收款系统** | 服务器使用 xpub 生成新地址 | ✅ 安全（无签名能力） |
| **只读监控** | 监控多个地址的余额和交易 | ✅ 安全 |
| **冷热分离** | 冷钱包生成 xpub，热钱包生成地址 | ✅ 安全 |

### ⚠️ 风险提示

```
如果攻击者同时获得：
1. xpub（扩展公钥）
2. 任何一个子私钥（child private key）

则攻击者可以推导出：
- 主扩展私钥（master private key）
- 所有其他子私钥

后果：所有资产被盗
```

**防护**：
- 不要在同一个地方存储 xpub 和任何私钥
- 定期轮换 xpub（创建新账户）

## 安全备份最佳实践

### 备份优先级

| 优先级 | 备份内容 | 存储方式 | 数量 |
|--------|----------|----------|------|
| **P0（必须）** | 助记词 | 纸质/金属板 | 至少 2 份 |
| **P1（强烈建议）** | Passphrase | 纸质，与助记词分开 | 至少 2 份 |
| **P2（可选）** | 账户路径记录 | 纸质/加密数字存储 | 1 份 |

### 存储方式对比

| 方式 | 优点 | 缺点 | 推荐度 |
|------|------|------|--------|
| **纸质备份** | 便宜、简单 | 怕水火、会损坏 | ✅ 基础方案 |
| **金属助记词板** | 防水防火防腐蚀 | 成本较高 | ✅✅ 推荐 |
| **加密 USB** | 可存储额外信息 | 可能损坏、丢失 | ⚠️ 辅助方案 |
| **云盘/截图** | 方便 | ❌ 极度危险 | ❌ 绝对禁止 |

### 安全存储 Checklist

- [ ] 助记词至少备份 2 份
- [ ] 异地存放（不同物理位置）
- [ ] 使用金属板或防火袋
- [ ] 绝不拍照、截图、存云盘
- [ ] 定期演练恢复流程（每 6-12 个月）
- [ ] 考虑设置继承人或信托方案
- [ ] 大额资产使用多签或硬件钱包

## 硬件钱包：大额资产首选

### 为什么需要硬件钱包

| 软件钱包 | 硬件钱包 |
|----------|----------|
| 私钥在联网设备 | 私钥在离线设备 |
| 可能被木马窃取 | 物理隔离，无法远程窃取 |
| 适合小额日常使用 | 适合大额长期存储 |
| 免费 | 需购买（$50-200） |

### 主流硬件钱包

| 品牌 | 价格 | 特点 | 推荐场景 |
|------|------|------|----------|
| **Ledger Nano X** | ~$150 | 蓝牙、移动友好 | 日常使用 |
| **Trezor Model T** | ~$220 | 开源、触摸屏 | 安全优先 |
| **OneKey** | ~$150 | 开源、多链支持 | 性价比 |
| **SafePal S1** | ~$50 | 二维码、无蓝牙/WiFi | 极致隔离 |

## 账户抽象（AA）：钱包的未来

### 传统钱包 vs AA 钱包

| 特性 | 传统 EOA 钱包 | AA 钱包（智能合约） |
|------|--------------|-------------------|
| **控制方式** | 单一私钥 | 可编程逻辑 |
| **Gas 支付** | 必须用 ETH | 可用代币代付 |
| **交易批处理** | 需多笔交易 | 可批量执行 |
| **恢复机制** | 助记词唯一 | 社交恢复、多签 |
| **权限管理** | 全有或全无 | 细粒度权限（限额、时间锁） |

### 核心标准

| 标准 | 说明 | 状态 |
|------|------|------|
| **ERC-4337** | 无需共识层改动的 AA 方案 | ✅ 已部署 |
| **EIP-7702** | EOA 临时委托代码执行 | 🚧 开发中 |
| **EIP-3074** | EOA 授权操作码 | ❌ 已放弃 |

### 用户价值

1. **Gas 代付**：DApp 可替用户支付 Gas，降低门槛
2. **社交恢复**：通过信任的守护者恢复账户，无需助记词
3. **批量交易**：一次签名执行多个操作
4. **权限降级**：日常使用低权限密钥，大额操作需要高权限
5. **订阅支付**：设置自动扣款限额

## ENS：可读地址

### 什么是 ENS

以太坊域名服务（Ethereum Name Service），将 `0x...` 长地址映射为 `name.eth`。

### 价值

| 优势 | 说明 |
|------|------|
| **降低错误率** | 输错 `vitalik.eth` 比输错 `0x...` 难得多 |
| **品牌身份** | 项目可使用 `project.eth` 作为官方地址 |
| **用户体验** | 新用户更容易理解和记忆 |
| **多链支持** | 一个 ENS 可映射多个链的地址 |

## 你要记住的 6 件事

1. ✅ **钱包管的是密钥，不是资产本体**
2. ✅ **主流方案是助记词 + HD 钱包，不是 JBOK**
3. ✅ **助记词安全是自托管的生命线**（离线物理备份）
4. ✅ **Passphrase 提升安全，但也提升"自锁死"风险**
5. ✅ **AA 的方向是让账户更智能、更可恢复、更低门槛**
6. ✅ **好的钱包策略 = 安全 + 恢复 + 使用体验三者平衡**

## 自测题

**题目**：为什么说"把助记词存在手机备忘录里，再加个复杂密码"依然是高风险做法？

**答案要点**：
1. **电子明文存储暴露面大**（云同步、木马、截屏、备份泄漏）
2. **密码只保护应用层**，不等于真正隔离私钥材料
3. **助记词一旦泄露，攻击者可在别的设备恢复钱包**（密码无效）
4. **更稳妥的是**：离线物理备份 + 分地存放 + 定期恢复演练

## 进阶实践

### 场景 1：从助记词恢复钱包

```javascript
const { Wallet } = require('ethers');

// 助记词（12 或 24 词）
const mnemonic = 'word1 word2 word3 ... word12';

// 恢复钱包（默认路径 m/44'/60'/0'/0/0）
const wallet = Wallet.fromPhrase(mnemonic);
console.log('地址:', wallet.address);
console.log('私钥:', wallet.privateKey);

// 指定路径恢复
const walletWithPath = Wallet.fromPhrase(mnemonic, undefined, "m/44'/60'/1'/0/0");
console.log('第二账户地址:', walletWithPath.address);
```

### 场景 2：使用 xpub 生成收款地址

```javascript
const { HDNodeWallet } = require('ethers');

// xpub（扩展公钥）
const xpub = 'xpub...';

// 从 xpub 派生收款地址（不需要私钥）
const hdNode = HDNodeWallet.fromExtendedKey(xpub);

// 生成前 10 个收款地址
for (let i = 0; i < 10; i++) {
  const child = hdNode.derivePath(`0/${i}`);
  console.log(`地址 ${i}:`, child.address);
}
```

### 场景 3：定期恢复演练

```bash
# 建议每 6-12 个月执行一次

1. 找一个新设备（未安装过钱包）
2. 从助记词恢复钱包
3. 验证所有地址和余额正确
4. 确认 Passphrase（如果使用）也能正确恢复
5. 记录恢复过程中遇到的问题并改进备份策略
```

## 本章核心

第 5 章真正要你建立的是"**钱包工程思维**"：

> 你管理的不是 App，而是**资产控制权**；标准化备份和恢复流程，远比追求花哨技巧更重要。

**开发者视角**：
- 理解钱包架构有助于设计更好的 DApp 交互（如 AA 钱包集成）
- 安全备份策略是项目方应该教育用户的重要内容
- 钱包用户体验直接影响 Web3 的采用率
