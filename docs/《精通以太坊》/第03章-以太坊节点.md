# 第03章 以太坊节点（Web3开发者精简版）

> 状态：已完成（优化版）
> 目标：理解节点架构、双客户端协作、节点类型差异、JSON-RPC 通信机制

## 一句话版

以太坊节点是**分层协作的分布式系统**，Merge 后必须由"执行客户端 + 共识客户端"共同组成。

## 核心概念速览

### Merge 前后的架构变化

| 时期 | 架构 | 说明 |
|------|------|------|
| **Merge 前（PoW）** | 单客户端 | 一个程序完成执行 + 共识 |
| **Merge 后（PoS）** | 双客户端 | 执行层 + 共识层分离协作 |

### 双客户端架构详解

| 客户端类型 | 职责 | 核心功能 | 代表实现 |
|-----------|------|----------|----------|
| **执行客户端（EL）** | 算账 + 跑程序 | 交易执行、EVM、状态更新 | Geth、Nethermind、Reth |
| **共识客户端（CL）** | 拍板 + 定历史 | PoS 共识、区块提议、终局性 | Prysm、Lighthouse、Teku |

**类比理解**：
- 执行层 = 会计（负责记账和计算）
- 共识层 = 审计委员会（负责确认账本正确性）

## 主流客户端矩阵

### 执行客户端（5 大实现）

| 客户端 | 语言 | 特点 | 使用场景 |
|--------|------|------|----------|
| **Geth** | Go | 最成熟、最广泛 | 默认选择、文档最全 |
| **Nethermind** | C# | 高性能、企业级 | 交易所、机构节点 |
| **Besu** | Java | 企业友好、权限控制 | 私有链、联盟链 |
| **Erigon** | Go | 存储优化、归档快 | 历史数据查询、索引服务 |
| **Reth** | Rust | 最新、性能优 | 前沿探索、Rust 生态 |

### 共识客户端（5 大实现）

| 客户端 | 语言 | 特点 | 使用场景 |
|--------|------|------|----------|
| **Prysm** | Go | 最流行、功能全 | 验证者节点首选 |
| **Lighthouse** | Rust | 性能优、轻量 | 资源受限环境 |
| **Teku** | Java | 企业级、稳定性高 | 机构验证者 |
| **Nimbus** | Nim | 轻量、IoT 友好 | 低功耗设备 |
| **Lodestar** | TypeScript | JS/TS 生态 | Web 开发者友好 |

**关键认知**：
- 可以**自由搭配**执行层和共识层（如 Geth + Lighthouse）
- 客户端多样性是以太坊安全的重要组成部分（单一客户端 bug 不会导致全网瘫痪）

## 节点类型对比

| 类型 | 存储内容 | 磁盘需求 | 用途 | 推荐度 |
|------|----------|----------|------|--------|
| **归档节点（Archive）** | 全部历史状态 | ~12 TB+ | 历史查询、索引服务 | 特殊需求才用 |
| **完整节点（Full）** | 最新状态 + 部分历史 | ~1-2 TB | 独立验证、隐私查询 | ✅ 推荐 |
| **轻节点（Light）** | 区块头 + 验证证明 | ~10 GB | 移动端、快速同步 | 开发调试 |
| **远程客户端** | 无，依赖外部 RPC | 0 | 钱包、DApp | ⚠️ 信任第三方 |

### 开发者环境选择

| 环境 | 同步时间 | 成本 | 适合场景 | 推荐度 |
|------|----------|------|----------|--------|
| **主网全节点** | 数小时 ~ 数天 | 高（硬件 + 带宽） | 生产、深度研究 | 高级用户 |
| **测试网节点** | 数十分钟 ~ 数小时 | 中 | 开发调试 | ✅ 推荐 |
| **本地节点（Anvil）** | 即时 | 低 | 单元测试、快速迭代 | ✅ 开发首选 |
| **公共 RPC** | 无 | 免费/付费 | 快速接入 | ⚠️ 有速率限制 |

## 我是否需要跑全节点？

### 决策树

```
是否用于生产环境？
├─ 是 → 跑主网全节点（Geth + Prysm）
└─ 否 → 是否需要独立验证？
        ├─ 是 → 跑测试网全节点
        └─ 否 → 使用公共 RPC 或本地节点
```

### 跑全节点的优缺点

**优点**：
- ✅ 不依赖第三方，独立验证交易和状态
- ✅ 查询隐私（不暴露查询内容给服务商）
- ✅ 对网络去中心化和抗审查有贡献
- ✅ 学习理解协议底层机制

**成本**：
- ❌ 硬件要求高（磁盘 1-2 TB、内存 16 GB+、CPU 4 核+）
- ❌ 首次同步慢（快照同步仍需数小时）
- ❌ 需要持续维护和升级（跟随网络升级）
- ❌ 带宽消耗大（持续 P2P 通信）

## 快速同步机制

### 为什么需要快速同步

历史上有 DoS 攻击区间，完整重放所有交易会非常慢（数周）。现代客户端使用优化同步策略：

| 同步方式 | 适用层 | 原理 | 时间 |
|----------|--------|------|------|
| **Snap Sync** | 执行层 | 下载状态快照 + 最近区块 | 数小时 |
| **Checkpoint Sync** | 共识层 | 从可信检查点开始同步 | 数分钟 |

**建议**：开发环境优先使用快照同步，无需等待完整历史同步。

## 跑节点实操指南

### 环境准备

```bash
# 1. 创建目录结构
mkdir -p ~/ethereum-node/{execution,consensus,jwt}

# 2. 生成 JWT 密钥（执行层和共识层的握手凭证）
openssl rand -hex 32 > ~/ethereum-node/jwt/jwt.hex
```

### 启动执行客户端（Geth 示例）

```bash
geth \
  --http --http.addr 0.0.0.0 --http.port 8545 \
  --http.api eth,net,web3,txpool,debug \
  --authrpc.addr 0.0.0.0 --authrpc.port 8551 \
  --authrpc.vhosts localhost \
  --authrpc.jwtsecret ~/ethereum-node/jwt/jwt.hex \
  --datadir ~/ethereum-node/execution \
  --syncmode snap
```

### 启动共识客户端（Prysm 示例）

```bash
prysm beacon-chain \
  --execution-endpoint=http://localhost:8551 \
  --jwt-secret=~/ethereum-node/jwt/jwt.hex \
  --checkpoint-sync-url=https://checkpoint-sync.sepolia.ethpandaops.io \
  --datadir ~/ethereum-node/consensus
```

### 关键配置说明

| 参数 | 说明 | 安全注意 |
|------|------|----------|
| `--http.addr 0.0.0.0` | 允许外部访问 RPC | ⚠️ 生产环境应限制 IP |
| `--authrpc.jwtsecret` | JWT 密钥路径 | 🔒 必须保密 |
| `--checkpoint-sync-url` | 检查点同步源 | ✅ 加速初始同步 |

## JSON-RPC 接口详解

### 什么是 JSON-RPC

**定义**：节点对外提供服务的标准 API 协议，使用 HTTP/WebSocket 传输 JSON 格式数据。

**本质**：所有钱包、DApp、开发库（ethers.js、web3.py）都通过 JSON-RPC 与节点通信。

### 常用 RPC 方法

| 方法 | 功能 | 示例 |
|------|------|------|
| `eth_blockNumber` | 查询最新区块号 | `{"jsonrpc":"2.0","method":"eth_blockNumber","params":[],"id":1}` |
| `eth_getBalance` | 查询地址余额 | `{"method":"eth_getBalance","params":["0x...","latest"]}` |
| `eth_sendRawTransaction` | 发送已签名交易 | 广播交易到网络 |
| `eth_call` | 只读调用合约函数 | 不改变状态，不消耗 Gas |
| `eth_estimateGas` | 预估 Gas 消耗 | 发送交易前预估成本 |
| `eth_getTransactionReceipt` | 查询交易回执 | 查看交易执行结果 |

### 使用示例（curl）

```bash
# 查询以太坊最新版本
curl -X POST http://localhost:8545 \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","method":"web3_clientVersion","params":[],"id":1}'

# 查询最新区块号
curl -X POST http://localhost:8545 \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","method":"eth_blockNumber","params":[],"id":1}'

# 查询地址余额（返回 wei，需转换）
curl -X POST http://localhost:8545 \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","method":"eth_getBalance","params":["0x742d35Cc6634C0532925a3b844Bc9e7595f2bD38","latest"],"id":1}'
```

### 公共 RPC 服务

| 服务商 | 免费额度 | 适用场景 |
|--------|----------|----------|
| **Infura** | 100,000 次/天 | 开发、小规模生产 |
| **Alchemy** | 300,000,000 CU/月 | 开发、生产 |
| **QuickNode** | 试用额度 | 高性能需求 |
| **Ankr** | 免费公共端点 | 快速测试 |
| **Public Node** | 完全免费 | 非商业用途 |

**注意**：生产环境建议自建节点或使用付费 RPC 服务，避免速率限制和单点故障。

## 你要记住的 5 件事

1. ✅ **Merge 后以太坊节点 = 执行客户端 + 共识客户端**，必须同时运行
2. ✅ **执行层负责计算**（EVM、交易执行），**共识层负责定链**（PoS、终局性）
3. ✅ **全节点最独立但成本高**，开发阶段优先测试网或本地链
4. ✅ **JWT 密钥是两层客户端的内部握手凭证**，必须保密
5. ✅ **JSON-RPC 是一切钱包与 DApp 交互的底层入口**，理解它对排障至关重要

## 自测题

**题目**：为什么现在单独跑 Geth 不能算"完整可用的主网节点"？

**答案要点**：
1. Geth 属于执行客户端，只负责执行层（交易执行、状态更新）
2. Merge 后主网共识由 PoS 客户端负责（区块提议、验证、终局性）
3. 没有共识客户端，节点无法正确跟随当前共识链头与 finality
4. 所以必须执行层 + 共识层同时运行，通过 JWT 认证通信

## 进阶实践

### 场景 1：监控节点同步状态

```bash
# Geth 同步状态
curl -X POST http://localhost:8545 \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","method":"eth_syncing","params":[],"id":1}'

# 返回 false = 已同步完成
# 返回对象 = 仍在同步中（显示 currentBlock、highestBlock）
```

### 场景 2：检查客户端版本

```bash
# 执行客户端版本
curl -X POST http://localhost:8545 \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","method":"web3_clientVersion","params":[],"id":1}'

# 共识客户端版本（通过 API）
curl http://localhost:5052/eth/v1/node/version
```

### 场景 3：使用 Docker 快速部署

```yaml
# docker-compose.yml
version: '3.8'
services:
  geth:
    image: ethereum/client-go:latest
    command: --http --http.addr 0.0.0.0 --syncmode snap
    ports:
      - "8545:8545"
      - "8551:8551"
    volumes:
      - geth-data:/root/.ethereum
      - ./jwt:/jwt
  
  prysm:
    image: gcr.io/prysmaticlabs/prysm/beacon-chain:latest
    command: --execution-endpoint=http://geth:8551 --jwt-secret=/jwt/jwt.hex
    depends_on:
      - geth
    volumes:
      - prysm-data:/data
      - ./jwt:/jwt

volumes:
  geth-data:
  prysm-data:
```

## 本章核心

第 3 章真正想让你明白的是：

> 以太坊不是一个"单程序系统"，而是一套**分层协作的节点架构**；懂这个架构，你后面的开发、部署、运维才不会迷路。

**开发者视角**：
- 理解节点架构是排查问题的基础（是执行层问题还是共识层问题？）
- 选择合适的节点类型平衡成本和独立性
- 掌握 JSON-RPC 接口是链上交互的基石
