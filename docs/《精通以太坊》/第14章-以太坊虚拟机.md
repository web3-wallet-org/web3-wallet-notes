## 一、EVM 架构概览

### EVM 核心组件

```mermaid

    A["合约代码<br/>Solidity"] -->|编译| B["EVM 字节码"]

    C --> D["内部组件<br/>PC<br/>Stack<br/>Memory<br/>Storage<br/>Gas Counter<br/>State Trie"]
    C -->|状态变更| E["链上状态<br/>账户余额<br/>合约存储<br/>交易记录"]
```

#### 组件拆解（详细版）

##### 1. PC（Program Counter）
- 主要职责：指向当前执行的 opcode 位置，执行后自动前进或跳转。
- 常见指令：`JUMP` `JUMPI` `JUMPDEST`
- 生命周期：单次调用内有效。
- Gas 特征：跳转本身较便宜，非法跳转会直接失败。
- 开发常见坑：跳到非 `JUMPDEST` 会 `REVERT`，手写汇编容易踩坑。

##### 2. Stack（栈）
- 主要职责：EVM 核心计算区，算术/逻辑/比较都在栈顶完成。
- 常见指令：`PUSHn` `POP` `DUPn` `SWAPn` `ADD` `MUL`
- 生命周期：单次调用内有效。
- Gas 特征：栈操作通常很便宜（常见 3 Gas 级别）。
- 开发常见坑：栈深超过 1024 会异常；`stack too deep` 常见于复杂函数。

##### 3. Memory（内存）
- 主要职责：临时字节数组，用于函数参数、返回值、临时变量。
- 常见指令：`MLOAD` `MSTORE` `MSTORE8` `MSIZE`
- 生命周期：单次调用结束即清空。
- Gas 特征：扩容越大越贵，成本随内存增长上升。
- 开发常见坑：大数组放 memory 会涨 Gas；memory 不会跨交易持久化。

##### 4. Storage（存储）
- 主要职责：保存合约持久化状态（状态变量）。
- 常见指令：`SLOAD` `SSTORE`
- 生命周期：跨交易持久存在。
- Gas 特征：最贵区域之一，写入尤其昂贵。
- 开发常见坑：循环中频繁 `SSTORE` 很烧 Gas；升级合约要注意槽位冲突。

##### 5. Gas Counter（Gas 计数器）
- 主要职责：追踪剩余 Gas，保证执行可终止。
- 常见字段：`gasleft()`（Solidity） / `GAS`（opcode）
- 生命周期：单次交易/调用内计算。
- Gas 特征：每条指令都会扣 Gas，耗尽即中止并回滚状态。
- 开发常见坑：低估 worst-case Gas，主网交易可能失败。

**直觉理解：Gas 就像燃料**

```
Gas 余额：100

执行 PUSH1   → 剩 97
执行 PUSH1   → 剩 94
执行 ADD     → 剩 91
执行 SSTORE  → 需要 20000，但只剩 91

              ❌ Out of Gas
              → 交易中止
              → 所有状态改变撤销（回到执行前）
              → 已消耗的 Gas 不退还
```

> Gas 的本质是防止无限循环攻击网络——让每一步计算都有成本，让恶意的无限循环自动停止。

##### 6. State Trie（状态树）
- 主要职责：承诺全网状态（账户、余额、storageRoot 等）。
- 关键字段：区块头 `stateRoot`
- 生命周期：区块级持续演进。
- Gas 特征：冷访问更贵，热访问更便宜（EIP-2929）。
- 开发常见坑：把链上状态访问当成本地读取，会低估 Gas。

##### 7. Call Context（调用上下文）
- 主要职责：提供 `msg.sender` `msg.value` `calldata` `address(this)` 等信息。
- 常见指令：`CALLER` `CALLVALUE` `CALLDATALOAD` `ADDRESS`
- 生命周期：每次外部/内部调用都会创建新上下文。
- Gas 特征：上下文切换伴随调用成本。
- 开发常见坑：`CALL` 与 `DELEGATECALL` 上下文差异会引发权限漏洞。

#### 一次调用里它们如何协作

1. `PC` 从字节码第 0 位开始取指令。
2. 指令把数据压入 `Stack`，在栈顶完成计算。
3. 需要临时缓冲时写入 `Memory`，例如 ABI 编解码。
4. 读写状态变量时访问 `Storage`（最影响 Gas）。
5. 每执行一步都扣减 `Gas Counter`，不足则中止。
6. 调用结束后，成功则把状态写回并反映到 `State Trie`，失败则回滚状态。

#### 对照调试器看这 3 个最关键信号

1. `stack` 变化：确认计算顺序是否符合预期。  
2. `memory` 扩容：定位 Gas 异常增长点。  
3. `storage` 读写次数：判断是否存在可优化的状态访问。

### EVM vs 传统虚拟机

| 特性 | EVM | JVM (Java) | V8 (JavaScript) | 优先级 |
|------|-----|-----------|----------------|--------|
| **执行环境** | 去中心化节点网络 | 单台机器 | 浏览器/Node.js | ⭐⭐⭐⭐⭐ |
| **确定性** | 强确定性（所有节点结果一致） | 确定性 | 确定性 | ⭐⭐⭐⭐⭐ |
| **资源限制** | Gas限制 | 内存限制 | 内存限制 | ⭐⭐⭐⭐⭐ |
| **状态持久化** | 区块链存储 | 本地文件系统 | 本地存储 | ⭐⭐⭐⭐⭐ |
| **安全性** | 沙箱隔离（无法访问外部） | 可访问系统资源 | 受限访问 | ⭐⭐⭐⭐⭐ |
| **性能** | 较慢（~20 TPS） | 快 | 快 | ⭐⭐⭐ |

## 二、EVM 执行模型详解

### 1. 基于栈的架构

```
EVM 是栈式虚拟机，所有操作都在栈上进行：

示例：计算 a + b * c

Solidity:
  uint result = a + b * c;

EVM 字节码执行过程：

栈操作：
PUSH1 a        → Stack: [a]
PUSH1 b        → Stack: [a, b]
PUSH1 c        → Stack: [a, b, c]
MUL            → Stack: [a, (b*c)]
ADD            → Stack: [(a+b*c)]

最终结果在栈顶
```

**栈的特性**：
- 最大深度：1024层
- 每项：256位（32字节）
- 操作：PUSH（入栈）、POP（出栈）
- Gas消耗：栈操作非常便宜（3 Gas）

**直觉理解：栈顶**

把栈想象成一叠盘子，栈顶就是最上面那个盘子，你只能操作它：

```
放盘子（PUSH）：只能往最上面放
拿盘子（POP） ：只能从最上面拿
做运算（ADD） ：拿走顶上两个，结果放回顶上
```

示例：计算 3 + 5

```
执行 PUSH 3    执行 PUSH 5    执行 ADD
               
  [ 3 ] 顶       [ 5 ] 顶       [ 8 ] 顶
                 [ 3 ]
```

所有指令只看栈顶的几个元素，下面的数据完全不动，等待被用到时再浮到顶部。

**32字节能装什么？**

```
32 个英文字符 ： "HelloWorldHelloWorldHelloWorldHH"
10 个汉字    ： "以太坊虚拟机栈深度限"（UTF-8 每个汉字3字节）
1 个以太坊地址：0x000000000000000000000000742d35Cc...（20字节，补零到32）
1 个 uint256 ：115792089237316195423570985008...（恰好填满）
```

**爆栈示例**：

```
PUSH 操作不断压栈但不弹出：
第 1024 次 PUSH → 栈深度 1024  ✅
第 1025 次 PUSH → 栈深度 1025  ❌ Stack overflow → 交易 revert
```

### 2. 内存（Memory）

**内存特性：**
- 易失性：每次交易后清零。
- 线性地址空间：`0` 到 `2^256-1`。
- 访问方式：字节寻址。
- Gas 成本：随内存扩容增长。

**内存布局（Solidity 常见约定）：**

| 地址区间 | 用途 |
|---|---|
| `0x00 - 0x3f` | 临时工作区（scratch space） |
| `0x40` | 空闲内存指针（free memory pointer） |
| `0x60` | 零槽位（zero slot） |
| `0x80` 之后 | 动态分配区（函数参数、局部变量、返回值 ABI 编码等） |

> 注：具体细节会随编译器版本和优化设置变化，但整体思路一致。

**内存操作示例**：
```solidity
// Solidity 代码
function testMemory() public pure returns (uint) {
    uint[] memory arr = new uint[](3);
    arr[0] = 1;
    arr[1] = 2;
    arr[2] = 3;
    return arr[0] + arr[1] + arr[2];
}

// 对应的 EVM 操作
MLOAD     // 从内存加载
MSTORE    // 存储到内存
MSIZE     // 获取内存大小
```

### 3. 存储（Storage）

```
存储特性：
- 持久化：交易结束后仍保留
- 键值对：256位键 → 256位值
- 地址空间：2^256 个槽位
- Gas成本：昂贵（读100 Gas，写20000 Gas）

存储布局（状态变量顺序）：

Slot 0: 第一个状态变量
Slot 1: 第二个状态变量
Slot 2: 第三个状态变量
...

合约创建时确定，不可更改
```

**存储 vs 内存对比**：

| 特性 | Storage | Memory | 优先级 |
|------|---------|--------|--------|
| **持久性** | 永久保存 | 交易结束清除 | ⭐⭐⭐⭐⭐ |
| **Gas成本** | 读100，写20000 | 读3，写3 | ⭐⭐⭐⭐⭐ |
| **用途** | 状态变量 | 临时变量、函数参数 | ⭐⭐⭐⭐⭐ |
| **访问速度** | 慢 | 快 | ⭐⭐⭐⭐ |
| **容量** | 2^256 槽位 | 无限制（但Gas限制） | ⭐⭐⭐ |

## 三、EVM 指令集（Opcodes）

### 1. 核心指令分类

| 分类 | 核心指令 | 用途 |
|------|---------|------|
| 栈操作 | PUSH / POP / DUP / SWAP | 压栈、弹栈、复制、交换 |
| 算术运算 | ADD / SUB / MUL / DIV | 加减乘除 |
| 位运算 | AND / OR / XOR / SHL / SHR | 按位操作、移位 |
| 内存操作 | MLOAD / MSTORE | 读写临时内存 |
| 存储操作 | SLOAD / SSTORE | 读写链上存储（最贵）|
| 控制流 | JUMP / JUMPI / STOP | 跳转、条件跳转、停止 |
| 调用操作 | CALL / DELEGATECALL | 调用其他合约 |
| 环境信息 | ADDRESS / CALLER / TIMESTAMP | 获取上下文信息 |
| 日志操作 | LOG0 - LOG4 | 写入事件日志 |

### 2. Gas 消耗详解

**关键指令 Gas 成本：**

| 操作类型 | Gas 成本 | 说明 |
|---------|---------|------|
| **STOP** | 0 | 停止执行 |
| **ADD, SUB** | 3 | 基础算术 |
| **MUL, DIV** | 5 | 乘除运算 |
| **SLOAD** | 100 (热) / 2100 (冷) | 读取存储 |
| **SSTORE** | 100 (更新) / 20000 (新增) | 写入存储（最贵） |
| **MLOAD, MSTORE** | 3 | 内存操作 |
| **JUMP, JUMPI** | 8 | 跳转指令 |
| **CALL** | 40 + 调用成本 | 外部调用 |
| **LOG0-LOG4** | 375 + 数据成本 | 事件日志 |
| **SHA3** | 30 + 6×字数 | 哈希计算 |
| **CREATE** | 32000 | 创建合约 |
| **SELFDESTRUCT** | 5000 (首次) / 0 (后续) | 自毁合约 |

Gas 优化技巧：
✅ 使用 memory 而非 storage（临时数据）
✅ 批量更新存储（减少 SSTORE 次数）
✅ 使用事件记录日志（比存储便宜10-20倍）
✅ 避免循环中的存储操作

## 四、合约执行流程

### 1. 交易到执行的完整流程

```
用户发起交易
    ↓
[1] 交易进入内存池（Mempool）
    ↓
[2] 矿工/验证者选择交易
    ↓
[3] 验证交易签名和 nonce
    ↓
[4] 扣除基础 Gas 费用（21000 Gas）
    ↓
[5] EVM 创建执行环境
    ├─ 初始化栈（空）
    ├─ 初始化内存（空）
    ├─ 加载合约存储
    └─ 设置环境信息（msg.sender, msg.value等）
    ↓
[6] 逐条执行字节码指令
    ├─ 从 Program Counter 读取指令
    ├─ 执行指令（可能修改栈/内存/存储）
    ├─ 更新 Gas 计数器
    └─ 如果 Gas 耗尽 → REVERT
    ↓
[7] 执行完成
    ├─ 成功 → 提交状态变更
    └─ 失败 → REVERT（回滚状态，消耗Gas）
    ↓
[8] 计算实际 Gas 消耗
    ├─ 退还剩余 Gas
    └─ 记录交易收据
    ↓
[9] 交易打包进区块
```

### 2. 合约调用类型

```solidity
// 四种调用方式对比

contract Target {
    uint public value;
    
    function setValue(uint _value) public {
        value = _value;
    }
    
    function getValue() public view returns (uint) {
        return value;
    }
}

contract Caller {
    Target public target;
    
    // 1. CALL - 最常用的调用
    function callSetValue(uint _value) public {
        // 修改目标合约状态
        // msg.sender = Caller 合约地址
        // msg.value = 0
        target.setValue(_value);
    }
    
    // 2. DELEGATECALL - 代理模式核心
    function delegateCallSetValue(uint _value) public {
        // 在 Caller 合约上下文中执行 Target 代码
        // 修改的是 Caller 的存储
        // msg.sender = 原始调用者
        // ⚠️ 风险：如果 Target 被恶意替换，可操纵 Caller 存储
    }
    
    // 3. STATICCALL - 只读调用
    function staticCallGetValue() public view returns (uint) {
        // 只能读取，不能修改状态
        // 如果 Target 尝试修改状态，会 REVERT
        return target.getValue();
    }
    
    // 4. CALLCODE (已废弃)
    // 类似 DELEGATECALL，但 msg.sender 不同
    // 不推荐使用
}
```

## 五、EVM 状态机

### 以太坊是状态机

**直觉理解：什么是状态机**

状态机 = 根据输入改变自身状态的机器。最简单的例子：地铁闸机。

```
         投币
[锁定] ──────→ [解锁]
  ↑               │
  └───────────────┘
       通过后自动锁定
```

| 当前状态 | 输入 | 下一状态 |
|--------|------|--------|
| 锁定   | 投币 | 解锁   |
| 解锁   | 通过 | 锁定   |
| 锁定   | 强行通过 | 锁定（不动）|

以太坊就是这个原理：**当前状态 + 输入（交易）→ 新状态**

```
状态机定义：
当前状态 + 交易 = 新状态

以太坊状态：
├─ 世界状态（World State）
│  ├─ 所有账户的余额
│  ├─ 所有合约的存储
│  └─ 账户 nonce
│
├─ 交易（Transaction）
│  ├─ from, to, value
│  ├─ data（调用合约的输入）
│  └─ gas, gasPrice
│
└─ 新状态
   ├─ 更新余额
   ├─ 更新合约存储
   └─ 递增 nonce

示例：
初始状态:
  Alice: 10 ETH
  Bob: 5 ETH
  合约X: storage[0] = 100

交易: Alice → Bob 转账 2 ETH

新状态:
  Alice: 8 ETH (-2 - gas)
  Bob: 7 ETH (+2)
  合约X: storage[0] = 100 (不变)
```

**全网重复执行：为什么结果一致**

全网结果一致，因为三个东西完全一样：

```
相同的起始状态
    +
相同的输入（交易）
    +
相同的规则（EVM 指令集）
    =
相同的结果
```

EVM 是一个**纯函数**：给定相同输入，输出必然一样，无论在哪台机器上运行。没有随机、没有网络请求、没有系统调用。

**全网重复执行的时序**：

```
你发出交易
    ↓
全网节点收到（放入 mempool）
    ↓
验证者打包成区块，自己先执行所有交易，算出状态根，写入区块头
    ↓
区块广播全网
    ↓
其他节点各自执行区块里每笔交易，自己算出状态根
    ↓
和区块头里的状态根比对：一致 → 接受区块 / 不一致 → 拒绝
```

这是用**效率**换**去中心化信任**的核心代价：同一件事，全网重复执行，但不需要信任任何人。

### 状态树结构

```
以太坊使用 Merkle Patricia Trie 存储状态：

世界状态树（State Trie）
├─ 账户A
│  ├─ nonce
│  ├─ balance
│  ├─ storageRoot → 存储树
│  └─ codeHash → 合约代码
│
├─ 账户B
│  └─ ...
│
└─ 合约C
   ├─ nonce
   ├─ balance
   ├─ storageRoot → 存储树
   │  ├─ slot 0: value
   │  ├─ slot 1: value
   │  └─ ...
   └─ codeHash

每个区块都有状态根哈希（stateRoot）
轻客户端可以通过 Merkle 证明验证账户状态
```

**直觉理解：三句话解释状态根**

**① 1000万账户浓缩成32字节**

哈希函数无论输入多大，输出永远是固定长度，通过树形结构层层哈希，最终汇总到根：

```
账户1 ──┐
账户2 ──┤→ 哈希A ──┐
账户3 ──┤           ├→ 哈希AB ──→ 根哈希（32字节）
账户4 ──┘→ 哈希B ──┘
  ...
```

改动任意一个账户的数据，根哈希立刻变化，无法隐瞒。

**② 根哈希写入区块头**

```
区块头
  区块号    : 18500000
  父块哈希  : 0xabc...
  状态根    : 0x4a5f8b2c...  <-- 锚定了全网所有账户状态
  交易根    : 0x9f3c1d7e...
  收据根    : 0x2b8e4f1a...
```

**③ 全网对着这个哈希对账**

```
节点 A 执行完 → 自己算出状态根：0x4a5f8b2c... ✅
节点 B 执行完 → 自己算出状态根：0x4a5f8b2c... ✅  → 共识达成
节点 C 执行完 → 自己算出状态根：0x4a5f8b2c... ✅

节点 D（被篡改）→ 算出：0x99999999... ❌ → 拒绝区块，重新同步
```

> 32字节是整个以太坊世界状态的"指纹"，指纹一样说明大家的世界完全相同。

**验证者造假会怎样**

```
验证者把自己余额从 1 ETH 改成 9999 ETH
    ↓
计算出伪造的状态根，写入区块头广播
    ↓
其他节点从真实状态出发，各自执行交易，自己算出真实根哈希
    ↓
两个哈希不一致 → 全网拒绝这个区块 ❌
    ↓
PoS 机制：验证者质押的 32 ETH 被罚没（Slashing），踢出验证者队列
```

控制 51% 验证者理论上可以强行通过，但需要数百亿美元，且攻击成功后 ETH 暴跌，攻击者自己损失最大。**系统设计让诚实出块比作恶收益更高。**

## 八、自测题

### 题目1：EVM 的存储（Storage）和内存（Memory）有什么区别？

**答案**：
| 维度 | Storage | Memory |
|------|---------|--------|
| **持久性** | 永久保存 | 交易结束清除 |
| **Gas成本** | 读100，写20000 | 读3，写3 |
| **用途** | 状态变量 | 临时变量、函数参数 |
| **容量** | 2^256 槽位 | 无限制 |

### 题目2：CALL 和 DELEGATECALL 的区别是什么？

**答案**：
| 维度 | CALL | DELEGATECALL |
|------|------|--------------|
| **执行上下文** | 目标合约 | 调用者合约 |
| **修改存储** | 目标合约存储 | 调用者合约存储 |
| **msg.sender** | 调用者合约地址 | 原始调用者 |
| **msg.value** | 传递 | 传递 |
| **用途** | 普通调用 | 代理模式、升级合约 |
| **风险** | 低 | 高（需信任目标合约） |

### 题目3：为什么 EVM 需要 Gas 机制？

**答案**：
1. **防止无限循环**：Gas 耗尽自动停止执行
2. **资源定价**：计算、存储、带宽都需要成本
3. **抗 DoS 攻击**：恶意交易需要支付费用
4. **激励矿工**：Gas 费奖励给打包交易的验证者
5. **优先级排序**：高 Gas 价格的交易优先被打包

## 本章总结

### 核心要点

1. **EVM 是基于栈的虚拟机**：所有操作在栈上进行，最大1024层
2. **三种存储区域**：Stack（栈）、Memory（内存，易失）、Storage（存储，持久）
3. **Gas 是资源计量单位**：防止滥用，保障网络安全
4. **以太坊是状态机**：交易驱动状态转换
5. **EVM 升级通过 EIP**：持续改进性能和功能
6. **EVM 兼容链众多**：但安全性和去中心化程度不同
