# 第10章 代币（Web3开发者精简版）

> 状态：已完成（优化版）
> 目标：快速掌握代币核心概念、标准差异、工程实践和安全要点

## 一句话版

代币是区块链上的**可编程权利载体**，不是"币的另一个叫法"。不同标准解决不同资产形态和交互问题。

## 核心概念速览

### 代币本质

- **词源**：token 源于古英语 tācen（符号/象征）
- **定义**：链上"可验证、可转移、可编程"的权利表示
- **承载内容**：
  - 货币（USDT、DAI）
  - 资源使用权（存储、算力）
  - 资产所有权（黄金、房地产映射）
  - 访问权限（独家社区、服务）
  - 治理投票权（DAO）
  - 身份和证明（学历、证书）

**关键认知**：代币是"权利抽象"，不只是"会涨跌的筹码"

### 同质化 vs 非同质化

| 类型 | 特点 | 标准 | 例子 |
|------|------|------|------|
| **同质化** | 每个单位可互换，无个体差异 | ERC-20 | 1 USDT = 另 1 USDT |
| **非同质化** | 每个单位唯一，tokenId 不同对象不同 | ERC-721 | 特定画作 ≠ 其他画作 |
| **混合多代币** | 单合约管理多种类型，支持批量操作 | ERC-1155 | 游戏金币+唯一装备 |

### 交易对手风险：内在 vs 外在

| 类型 | 特点 | 风险 | 例子 |
|------|------|------|------|
| **内在资产** | 权利和结算在链内闭环，受共识规则约束 | 无额外交易对手风险 | CryptoKitty、ETH |
| **外在资产映射** | 链上代币映射链下资产，依赖外部托管/法律 | 托管人风险、法律承认风险 | USDT、wBTC、房地产代币 |

**典型案例**：
- USDT/USDC：信任 Tether/Circle 公司托管法币储备
- wBTC：信任多签保管人持有真实 BTC
- 房地产代币：依赖法律体系和产权登记机构

## ERC-20（同质化代币标准）

### 为什么最常用

**价值不在"最完美"，而在"生态最兼容"**

### 核心接口（必须掌握）

```solidity
// 查询余额
function balanceOf(address account) external view returns (uint256);

// 直接转账（调用者→目标）
function transfer(address to, uint256 amount) external returns (bool);

// 授权额度（调用者授权 spender 代扣）
function approve(address spender, uint256 amount) external returns (bool);

// 代扣转账（需先 approve，广泛用于 DEX/路由器）
function transferFrom(address from, address to, uint256 amount) external returns (bool);

// 查询剩余授权额度
function allowance(address owner, address spender) external view returns (uint256);
```

### 关键事件

```solidity
event Transfer(address indexed from, address indexed to, uint256 value);
event Approval(address indexed owner, address indexed spender, uint256 value);
```

### 可选元数据接口（广泛支持）

```solidity
function name() external view returns (string);      // 代币名称
function symbol() external view returns (string);     // 代币符号
function decimals() external view returns (uint8);    // 小数位数（通常 18）
```

### 两条工作流

**1. transfer 直转**
- A → B 直接转账
- 调用者必须有足够余额
- 适用：个人对个人转账

**2. approve + transferFrom**
- A 先授权 B 可代扣额度
- B 再按额度代转
- 适用：DEX、金库、支付代理、自动化策略
- **注意**：这套机制很强，但最容易被误用（无限授权是典型坑）

### ⚠️ ERC-20 常见坑点（开发者必看）

1. **代币不是 ETH**：转账代币需要支付 gas（通常是 ETH），钱包没 ETH 就转不动
2. **转到不支持的合约地址会永久卡死**：普通转账只改余额，合约若无接收逻辑，代币就"困"在里面
3. **approve 机制容易被钓鱼**：无限授权 `approve(type(uint256).max)` 一旦私钥泄露，所有代币可能被盗
4. **代币行为不等同 ETH**：代币转账是合约调用，失败率和 gas 消耗与 ETH 原生转账不同
5. **重入攻击风险**：如果代币合约在转账前调用外部合约，可能被重入攻击

### ERC-2612（permit）- 签名授权

**解决问题**：用链下签名替代一次链上 approve 交易

**工作流程**：
1. 用户链下签名（零 gas）
2. 第三方提交 permit（链上，一次交易）
3. 降低授权成本和门槛

**核心价值**：
- 首次使用 DApp 无需先 approve 再 swap，一步到位
- 可设置过期时间，避免长期授权风险
- USDC、DAI 等主流稳定币已支持

## ERC-721（NFT 标准）

### 核心认知

- `tokenId → owner` 的唯一映射
- 资产是"一件一件"而非"余额总数"
- 每个 tokenId 对应独特元数据（图片、属性、描述）

### 核心接口

```solidity
// 查询所有者
function ownerOf(uint256 tokenId) external view returns (address);

// 安全转账（检查接收方是否支持 ERC-721，推荐用这个）
function safeTransferFrom(address from, address to, uint256 tokenId) external;

// 普通转账（不检查接收方，可能丢币）
function transferFrom(address from, address to, uint256 tokenId) external;

// 授权单个 tokenId
function approve(address to, uint256 tokenId) external;

// 授权所有 tokenId（常用于交易市场）
function setApprovalForAll(address operator, bool approved) external;
```

### 适用场景

- 收藏品（CryptoPunks、BAYC）
- 游戏道具（唯一武器、装备）
- 凭证和证书（学历、资格认证）
- 现实资产映射（房产证、车辆所有权）
- 域名（ENS）
- 会员资格（独家社区访问权）

## ERC-1155（多代币标准）

### 核心特性

- **混合模式**：单合约同时管理同质化+非同质化代币
- **批量操作**：一次性转移/查询多种代币，大幅节省 gas
- **工程化优势**：减少部署成本，适合复杂资产系统

### 工程收益

1. 减少部署和交互成本（不需要为每种代币部署新合约）
2. 批量转移更省 gas（适合游戏内批量交易）
3. 更适合游戏、元宇宙、复杂经济系统

### ⚠️ 安全注意事项

- **重入风险**：接收方合约可能在回调中再次调用转账
- **DoS 风险**：批量转账中某个接收方 revert 会导致整个交易失败
- **实现复杂度**：比 ERC-20/721 更复杂，需要仔细审计

## 其他重要标准

| 标准 | 解决问题 | 现状 |
|------|----------|------|
| **ERC-223** | 防止代币误转到合约地址而丢失（检测目标并调用 tokenFallback） | 未被广泛采用 |
| **ERC-777** | ERC-20 增强版，支持 hooks（转账前后触发回调） | 部分项目使用，但有重入风险 |
| **ERC-1400** | 证券型代币标准（合规检查、白名单、转让限制） | 受监管资产使用 |
| **EIP-165** | 接口检测（`supportsInterface` 查询合约能力） | 广泛用于互操作性 |

**注意**：EIP-165 虽有用，但恶意合约可能谎报支持，仍需业务层校验。

## 监管视角："这是鸭子！"

**证券属性风险**（Howey Test）：
监管机构用以下标准判断代币是否属于证券：
1. 是否有资金投入？
2. 是否投入共同企业？
3. 是否有获利预期？
4. 利润是否来自他人努力？

**现实提醒**：
- 许多项目试图标记为"实用代币"规避监管
- 但监管看实质不看标签："像鸭子就是鸭子"
- 2025 年特朗普 meme 币一天市值 150 亿美元，突显投机狂潮

**开发者应思考**：
- 代币是否真的有必要？还是只为融资？
- 没有代币，协议还能跑吗？
- 代币承载了什么不可替代的功能？
- 设计是为长期可持续，还是短期流动性故事？

## 代币类型对比

| 类型 | 目的 | 价值来源 | 例子 |
|------|------|----------|------|
| **实用代币** | 提供服务/资源访问权限 | 平台功能和使用需求 | 存储网络代币 |
| **股权代币** | 代表所有权/控制权 | 项目成功和治理能力 | DAO 投票权、利润分成 |

**实践问题**：类别往往模糊，许多实用代币仍是投机性的。

## 最稳妥的工程路线

1. ✅ **优先采用成熟标准**（ERC-20/721/1155），不要重复造轮子
2. ✅ **优先采用成熟实现**（OpenZeppelin Contracts），经过大量审计和实战检验
3. ✅ **扩展需求最小化改动并专项审计**，任何自定义逻辑都要单独审查
4. ✅ **充分测试授权、转账、接收兼容性**（零值转账、最大授权、合约接收等）
5. ✅ **给用户明确的授权风险提示与撤销入口**
6. ✅ **考虑使用 permit（ERC-2612）提升用户体验**（特别是 DeFi）
7. ✅ **关注监管合规**，代币可能被视为证券时咨询法律顾问

## 自测题

**题目**：为什么不能"一个 ERC-20 走天下"？

**答案要点**：
1. ERC-20 适合同质化余额模型，不适合唯一资产（艺术品、房产证）
2. ERC-721/1155 解决 NFT 与多资产管理需求，每个 tokenId 可有不同元数据
3. ERC-2612 解决授权体验与 gas 痛点，通过签名授权减少链上交易
4. 不同标准服务不同业务语义，强行用 ERC-20 模拟 NFT 会失去唯一性
5. ERC-1155 批量操作大幅降低 gas，ERC-20 做不到

## 进阶思考

**场景**：设计去中心化游戏，有金币（同质化）、装备（非同质化）、材料（多种同质化）

**推荐方案**：**ERC-1155**
- 单合约管理所有资产，降低成本
- 金币/材料用同质化模式（supply > 1）
- 装备用非同质化模式（supply = 1）
- 批量转移适合游戏内交易
- 批量查询适合展示背包
